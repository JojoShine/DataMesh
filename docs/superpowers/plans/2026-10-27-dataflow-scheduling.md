# 数据流执行方式与直接调度

> **For agentic workers:** Use superpowers:executing-plans inline. 用户已确认产品边界；不重复申请常规编辑确认，不提交现有未跟踪仓库。

**Goal:** 单个批量数据流可以手动和定时执行；工作流作为可选编排；流式版本管理长驻作业。
**Architecture:** 扩展现有版本记录和调度表。版本 execution_mode 固定 batch/continuous，历史有流作业的版本迁移为 continuous，其余 batch，不改定义与执行快照。调度保留旧 workflow 请求并增加 dataflow 引用，复用队列、鉴权、参数和触发证据。
**Tech Stack:** Go/GORM/PostgreSQL、React/Ant Design、现有 Doris/Flink 执行器。
**Spec:** 本轮用户确认的三项职责及上一轮的一版本一种执行方式。

## Global Constraints
- 工作流不是单数据流执行或调度前置；不新增依赖和计算引擎。
- 新版本可选模式，旧版本不可修改；未传模式的修订继承原版本，新建默认 batch。
- 保留旧调度接口字段；数据流目标不能接受流式、草稿、停用或越权版本。
- 沿用字体、24px 区块间距、响应式和底部按钮规范。

## Review Focus
- 旧 workflow 调度与新 dataflow 调度都能触发真实运行，防重复、防重叠。
- 流式不能走批量运行、调度或工作流有界子任务入口。
- 运行时复核权限、版本状态和参数，不仅创建时校验。
- 历史定义/运行指纹不受模式迁移影响。
- 数据流入口与中央调度管理展示同一批计划，切换目标不得保留错误参数。

## 结果与实施决定
- 使用版本独立列保存模式，避免修改历史 definition/pinned JSON 指纹。
- 保留调度原 FK 列名，通过 target_kind 区分目标，旧 workflow 请求保持兼容。
- 直接调度复用 enqueueGovernanceFlow；没有创建隐式工作流。
- 历史版本同时被发布工作流引用且有流式记录时，迁移明确阻止，需要拆分后升级，不静默改模式。
- 独立复核发现的固定目标参数、共享参数覆盖、分页总数及历史混用迁移问题均已修复并加入回归。
- 用户于 2026-10-28 明确授权备份、更新数据库及合并部署；已随业务用途改动部署，迁移 32，线上校验通过。详见 `docs/validation/governance/2026-10-28-model-purpose-scheduling.md`。
