# 治理业务闭环补齐

用户批准已核实的五项缺口；先初始化和异常整改，再主数据资产化、发布策略、看板。直接执行，不使用子代理、减少重复测试、不提交Git。国产数据库缺联调实例不伪造验证，不扩大跨部门权限。

复用方案：现有21张业务表与六个空间；现有质量问题、派单/期限/事件/复测；现有不可变版本、数据流、Doris成果、目录和数据服务。避免另建整改系统或第二执行引擎。

1. 初始化：独立版本化、幂等的治理扩展初始化，引用已登记资源与发布流程，建立六类监测、标准关联、指标和场景方案，人口/法人建立主数据定义与真实匹配记录；敏感值维持现有保护。保留数据与原6资产。迁移包包含同一初始化脚本；运行事实、待审核事项与方案登记分开记录。
2. 统一整改：既有问题表支持数据流、监测和标准核验三种证据；责任人、期限、事件和通知共用；原执行与新复测必须同源、同固定配置与标准，不允许旧结果关闭。监测存在统一工单时由工单关闭同步原异常状态。只读计数不冒充质量通过。
3. 主数据资产化：冻结选定实体确认版本，建立仅本人可用的内部主数据快照作为普通数据流的受控输入；每次读取重核原匹配运行、派生权限、模型及主数据版本。生成正常数据流草稿，经发布、完整执行后进入普通成果核验、资产目录与数据服务。完整来源字段血缘保留，不自动公开或回写来源。内部快照不成为共享目录可选原始资源，不自动授予其他人员权限。
4. 发布策略：空间设置明确需审核的定义类型，可逐空间采用，现有空间默认兼容；启用后未登记变更申请也不能直接发布。沿用独立审核。工作流候选试跑复用真实编排执行并禁止发布审批任务实际发布，固定所有子版本，失败/质量不合格不可批准。初始化已有资产与定义保持，初始化追加配置完成后按设定启用策略；不假造人工审批记录。
5. 看板：按原空间/部门/本人范围汇总监测异常、标准覆盖、主数据冲突、指标/方案和待审发布；提供对应入口，不把初始化、定义数与执行成功混算。

验证：隔离PostgreSQL与Doris测试真实三种工单闭环、权限撤销、不可变主数据快照及成果血缘、必审入口和工作流试跑、看板隔离；前端相关检查与桌面窄屏核对。备份恢复演练增量迁移，保留原表与原资产；初始化用现有平台正常接口及幂等检查点，不覆盖现有业务数据。
