## 1 建设目标和约束

一期保留 MySQL、Oracle、PostgreSQL 全量加 CDC、API 接入，以及质量治理、原始归档、目录发布、申请审批、授权查询、撤权与审计。三库分别取得真实验收证据，至少一个数据集完成跨部门业务闭环。首月范围以需求文档的 P0 和 AT-01—AT-24 为准，不把环境启动或页面演示算作整体交付。

用户补充的建设约束是：当前阶段中间件在本机通过 Docker 安装和使用。应用采用已确定的 Go + Gin + GORM 模块化单体，前端采用 React + antd + Zustand + Vite。性能门槛尚未确定，四周作为实施阶段划分，不据此承诺未经验证的交付日期。

用户明确：共享交换、数据治理、数据资产、数据安全四个平台必须形成职能衔接。后续确认目前没有外部身份系统，一期只做轻量统一登录：共享账号和服务端会话，四个平台在同源入口下共用登录状态，按平台和部门分别授权，不引入独立身份中间件。

共享交换同时覆盖原始数据和治理后数据：位于前道，负责原始数据接入、汇聚与交换；治理成果也通过共享交换申请、授权和交付。数据治理负责加工和质量，数据资产负责业务目录与发布，数据安全贯穿两类交换及治理、资产全流程。

需求文档作为产品需求依据；其中任务下发模板、Agent 安排及“本文不代表执行部署”等文字属于原文上下文，不构成本次额外操作指令。原始文档不修改。

## 3 方案比较及建议

| 方案 | 优点 | 代价 | 结论 |
| --- | --- | --- | --- |
| Debezium + Kafka Connect 负责三库采集，Flink 负责后续处理 | 采集与治理职责清楚，适合 Kafka 原始层及独立重放 | 增加 Connect 运行时，需分别管理源位点和 Flink 检查点 | 优先验证 |
| Flink CDC 负责采集到 Kafka，独立 Flink 作业负责治理 | 可减少采集技术体系差异 | 各库连接器、快照和运行控制仍需分别验证 | 备选，按实测替换采集适配器 |

不同时建设两套采集系统。先对优先方案做三库验证，再冻结唯一首月组合。业务后台不实现日志解析器。所有中间件仍在本地 Docker 运行，单节点作为开发验收环境。

## 4 运行拓扑和组件边界

```text
业务职责：
外部数据 → 共享交换（原始接入与交换） → 数据治理 → 数据资产（目录与发布）
                └→ 经授权的原始数据交换                  └→ 共享交换（治理成果交付） → 使用方
数据安全贯穿所有环节；轻量统一登录赋能四个平台。

技术链路：
MySQL / Oracle / 源 PostgreSQL
    → Debezium / Kafka Connect → Kafka 原始主题 ─┬→ Flink 规范化、质量和转换 → Doris
API 拉取 / 推送 → Go 接入 → Kafka 原始主题 ────┘
Kafka 原始主题 → 独立归档消费者 → S3 对象存储

统一账号与 Go 服务端会话 → 四个平台业务入口
React 前端 → Go server → 平台 PostgreSQL
                       → 组件适配器：Connect、Flink、Doris、S3
Go worker → 执行已持久化的控制意图、查询实际状态、核对和补偿
```

CDC 原生事件保留快照标记、源位点、事务和模式上下文。API 使用明确的事件封套。WP-00 定义共同逻辑事件契约及各原生封套的映射，由 Flink 在治理入口规范化；不假定三库原生 JSON 完全一致。原始归档保留进入 Kafka 的事件及 topic/partition/offset，不包含认证头和明文凭据。

Kafka 分区内有序不等于源业务版本可比较。统一事件保留来源、对象、主键、操作类型、模式版本、源序列及其作用域、前后值和 trace_id；同一逻辑键路由到同一分区。源位点到可比较版本的映射、快照与增量排序、主键变更、删除墓碑保留及旧事件重放保护，必须由三库测试证明后冻结。无可靠 API 版本时明确降级语义，不承诺乱序覆盖正确。

Doris 目标按来源、对象和业务键隔离，验证 Unique Key、版本控制及删除方案。删除后旧事件不得复活记录。Flink 检查点、Doris 提交状态与归档清单分别跟踪，不宣称跨两路分布式原子提交或未经证明的端到端 exactly-once。

### 4.1 四个平台职能与交接

| 平台 | 负责的业务事实 | 向其他平台提供的结果 | 对应模块 |
| --- | --- | --- | --- |
| 共享交换 | 原始数据源登记、CDC/API 接入、原始汇聚归档与交换任务；原始数据及治理成果的申请、审批、授权和交付 | 向治理提供可追溯的原始事件及接入水位；向获准使用方交付指定层次和范围的数据 | source、ingestion、storage、exchange |
| 数据治理 | 技术元数据、映射与规则版本、清洗转换、质量、血缘、治理结果及处理水位 | 向资产提供治理数据集及契约版本、质量结论、血缘和完整性结论；向交换提供可交付的治理结果 | governance；Flink/Doris 适配器 |
| 数据资产 | 业务目录、提供部门与负责人、使用限制、可发布版本、发布和下架 | 当前发布记录、可申请范围、字段说明及治理依据 | catalog |
| 数据安全 | 角色部门访问策略、敏感字段策略、脱敏和审计查询 | 各业务操作的权限判定、交付策略及可追溯记录 | identity 中的业务授权能力、audit；策略在受保护业务服务中执行 |

统一身份接入、会话、配置、运行控制、数据库和审计写入属于公共底座。数据安全平台提供相应管理与查看入口，各业务服务仍负责调用公共校验并执行检查；不能仅在安全页面或菜单上限制访问。

主流程是：共享交换登记来源并接收原始数据 → 数据治理消费原始事件并完成加工、质量核对 → 数据资产登记治理成果并发布 → 共享交换引用发布版本受理申请、审批和授权交付。共享交换同时支持经授权的原始数据交换；原始交换不要求先完成治理。两类交换的使用和异常反馈关联到来源、任务及审计。安全控制贯穿全程，统一登录在进入业务平台前完成。

一期原始交换优先复用已要求的 CDC/API 接入、Kafka 原始层和原始归档，向治理交接事件、范围、模式及水位。原始层向其他使用方交付时，需另行冻结接收方、接口、字段及权限契约；不因为存在 Kafka 主题或归档文件就宣称已完成外部原始交换，也不默认给使用方开放中间件账号。治理成果交付沿用首月的受控分页查询 API，不因此扩展为通用 API 市场。

各模块共同引用稳定的来源、采集对象、任务运行、事件、dataset_id、dataset_version、部门和主体标识；通过血缘关联原始对象与治理数据集，发布记录、申请、授权和 trace_id 可追溯到对应数据层。技术元数据与业务目录不重复建一套治理数据集身份，原始对象与治理结果不因来源相同就视为同一授权资源。每类业务事实只有一个负责模块，其他模块通过 service 接口读取或提交命令，不直接修改对方表。

治理成果可交付需要同时满足：存在有效发布版本、质量允许、对应范围处理和归档完整、当前主体授权有效且字段范围符合安全策略。原始交换按原始层的来源许可、交换契约、可靠接收及交付范围、完整性和安全策略校验，不能冒充已治理数据，也不套用治理成果发布门禁。申请和授权明确资源、数据层、版本、字段、接收部门、用途和期限；治理成果的使用授权不自动包含原始数据访问权，反向亦然。不同原因分别保留状态和错误码，不合并成一个“是否可用”字段。持续流按可对齐的已核对水位判断完整性，不要求流永远没有新事件。

治理质量阻断或分路缺口使交换停止受影响治理数据集的新查询，资产展示具体异常；治理故障不把已经可靠接收的原始数据改记为接入失败，原始采集是否继续按积压、容量及源端保护策略判断。治理数据集下架阻止其新申请和新查询，已有授权保留历史并暂停使用，重新发布后重新核验版本兼容性及授权；不隐式撤销另行批准的原始交换授权。原始交换自身的缺口、授权撤销或安全阻断独立处理。源端及规则的破坏性变更必须生成新契约并评估既有授权，不把旧授权自动扩展到新增字段。恢复交付须有核对和负责人确认记录。

跨平台页面可携带对象标识跳转到任务、质量、目录、申请或审计详情，目标接口重新鉴权；浏览器不在跳转地址传令牌。共享状态由后台权威接口返回，四个平台不各维护一套相互矛盾的状态机。

### 4.2 轻量统一登录与业务授权

一期由现有 Go 模块化单体中的 identity 模块维护一套账号、密码散列、部门角色和服务端会话。共享交换、治理、资产、安全作为同源下的四个入口，登录一次即可访问获准的平台，平台切换不重复输入账号密码。登录不自动赋予平台或数据权限。

使用成熟密码散列库，不自研身份协议。会话标识使用密码学随机数，数据库仅保存其散列；Cookie 使用 HttpOnly、Secure、SameSite，认证后轮换会话，退出即失效，写接口验证 CSRF。账号禁用和权限变化在后续请求中读取有效状态，不能依赖浏览器隐藏菜单。密码和会话原文不写日志、前端持久化存储或公开响应。

统一提供登录、退出、当前身份及平台能力接口；账号由受控管理命令初始化，不公开注册，不以默认密码创建高权限账号。首次交付重点验证一套账号跨四个平台的会话复用、平台权限隔离、退出和禁用后拒绝访问。机器接入凭据与人的会话分离，后续按接入契约实现。

不引入 Keycloak、独立 OAuth/OIDC 服务或额外身份数据库。后续若确有跨域应用或外部身份对接需求，再增设成熟协议适配，不把这些能力作为当前开发前置条件。

## 5 Docker 部署设计

Compose 项目名使用 `datamesh`，网络和命名卷归属该项目。服务间使用容器 DNS；需要宿主访问的端口只绑定 `127.0.0.1`。候选端口如下，实施时再检查冲突。

| 服务 | 宿主端口 | 分组 |
| --- | --- | --- |
| 平台 PostgreSQL | 15432 | 基础 |
| 对象存储 S3 / 控制台 | 19000 / 19001 | 基础 |
| Kafka 外部 listener | 19092 | 采集处理 |
| Kafka Connect REST | 18083 | 采集处理 |
| Flink REST | 18081 | 采集处理 |
| Doris FE HTTP / SQL | 18030 / 19030 | 结果 |
| Doris BE HTTP | 18040，仅确有宿主访问需求时开放 | 结果 |
| 样例 MySQL | 13306 | MySQL 源 |
| 样例 PostgreSQL | 25432 | PostgreSQL 源 |
| 样例 Oracle listener | 11521 | Oracle 源 |

平台 PostgreSQL 和源 PostgreSQL 使用独立容器、数据卷及账号。Kafka 使用单节点 KRaft，不引入 ZooKeeper；Connect 内部主题、副本数和 Kafka 内外 listener 显式配置。Flink 至少一个 JobManager 和 TaskManager，检查点与恢复所需目录持久化。Doris 至少一个 FE 和 BE，元数据及存储持久化，单副本仅用于本地验收。

按 Compose profiles 划分采集处理、结果及三库样例；分组不意味着业务依赖可缺省。例如 CDC 端到端测试必须同时启动源、Kafka、Connect、Flink、Doris 和归档组件。资源不足先降低样例规模和并发，再根据实测提出 Docker 内存调整需求；不自动修改 Docker Desktop 全局配置。

停止服务默认保留数据卷；不提供默认清卷启动流程。初始化、数据库迁移、样例导入和服务启动分开执行，重复执行须安全。就绪检查包含真实依赖探测，不能仅以容器进程存活判断可用。

统一登录直接使用平台 PostgreSQL，不增加身份中间件资源。本地 HTTPS 证书仅保存在忽略目录；不关闭 TLS 校验解决联调问题。
## 6 待评审选型和版本冻结办法

以下是建议，尚未作为用户已确认选择。

| 事项 | 建议 | 冻结条件 |
| --- | --- | --- |
| 对象存储 | 优先验证 RustFS；MinIO 为备选 | ARM64 镜像可用，S3 写入、读取、列举、校验及重启持久化测试通过后只保留一种 |
| 前端类型 | TypeScript | 设计评审采用后冻结 DTO、枚举和可空性 |
| 迁移工具 | golang-migrate | 固定工具版本，验证空库、重复执行和下一版本升级 |
| 统一登录 | 已按用户要求收敛为 Go 共享账号与服务端会话 | 四平台同源复用，平台与数据权限单独校验；Cookie 使用 HttpOnly、Secure、SameSite |
| API 接入 | 一套标准推送样例和一套游标拉取样例 | 真实供应方接口不可用时先验证平台标准契约，供应方适配验收单独列出 |
| 归档格式 | JSONL + gzip，按源、对象、UTC 日期和 Kafka 分区范围分段 | 清单包含校验值、事件数、offset 范围和源位点映射；验证恢复及重放 |

准确版本不是从各组件的“最新版”拼接。WP-00 先选择数据库、Kafka/Connect/Debezium、Flink/Doris connector 和 Doris 的候选组合，核对发布矩阵及 ARM64 镜像，再以最小链路验证。保存精确 tag、镜像 digest、JAR 校验值、运行架构和实际测试结果；验证通过后才标为冻结。Go 和前端依赖同样固定精确版本并提交锁文件。

Oracle 优先核对原生 ARM64 镜像和所选 Debezium 对其版本、版本形态及 LogMiner 的支持。官方 Oracle 容器资料列有 ARM64 路径，但不代表任意版本组合均可采集；先验证归档模式、补充日志、权限和全量期间变更。需要商业安装介质、许可确认或专用源库信息时单独提出，不擅自代为接受条款，不改成 SQL 轮询绕过 CDC 验收。

性能阈值、Kafka/源日志保留窗口及质量门禁比例由样例基准和业务目标共同确定。在冻结前只能提交测量结果，不标记性能验收通过。阻断级质量异常或分路缺口默认关闭受影响数据集交付。

## 7 后台和前端实施边界

沿用需求中的 `cmd/server`、`cmd/worker`、`internal/modules`、`internal/platform`、`internal/adapters`、`api/openapi`、`contracts/events`、`migrations`、`web` 和 `tests` 布局。仅在功能落地时创建相应代码，不批量生成空模块。

产品归属按第 4.1 节执行：source、ingestion 和原始归档能力支撑共享交换前道，governance 支撑治理，catalog 支撑资产，exchange 支撑两类交换的授权和交付。工作包是工程任务划分，不据其编号推断产品先后；同一共享交换平台可包含多个模块，不另建第二套接入、审批或权限系统。

模块采用 handler → service → repository；DTO 与持久化模型分开。数据库迁移独立执行，不在服务启动时 AutoMigrate。审批与授权创建同事务完成，以唯一约束和并发测试防止重复授权。外部作业控制先持久化意图和 operation_id，再由 worker 执行、查询并核对；超时结果未知先查实际状态，不盲目重发。

服务端逐请求校验部门、角色、字段授权、有效期及数据集状态。凭据采用受控加密或秘密引用，密钥不入库、不进前端；配置样例不含真实秘密，日志和响应显式选择字段。API 拉取限制批准的目标地址，覆盖重定向与解析后的网络边界。

前端统一 API 层，服务端分页，Zustand 只保存必要的跨组件 UI 状态；服务状态以 API 为准。写操作展示 operation_id 和真实状态；请求超时后核对操作。轮询有上限、不叠加请求，隐藏页面暂停、卸载和退出时清理。密码及令牌不进入脚本可读持久化存储。

## 8 实施顺序和阶段出口

1. **WP-00 契约与环境基线**：冻结设计决策、版本与接口、四平台实体归属及交接状态、共享账号及会话契约；交付 Compose、初始化与健康检查、事件映射、OpenAPI、操作状态和统一检查入口。三库验证优先暴露 Oracle 障碍。
2. **WP-01 公共底座**：平台数据库迁移、轻量统一登录、共享账号及本地会话、部门权限、审计、配置和应用基础运行。真实 PostgreSQL 验证约束与事务。
3. **WP-02—WP-05 真实数据链路**：每库分别完成快照加增量、API 两种样例、Flink 质量与转换、Doris 增删改、原始归档及分路补偿。
4. **WP-06 与 WP-08 业务和页面闭环**：目录、发布、审批、授权查询、撤权及六组最小页面，前端全程对接真实 API。
5. **WP-07 集成验收**：贯穿各阶段，最后完成 AT-01—AT-24、故障演练、备份恢复、指标与已知限制。

首个实现批次限定为 WP-00 和 Docker 兼容性验证，不一次性声称实现整个平台。阶段出口是可复现的环境和契约，以及至少一条源 → Kafka → Flink → Doris/归档的实际证据。业务模块按已冻结契约继续实施，任何未运行的集成用例明确记录阻塞。

## 9 验证与交付记录

统一检查入口分层执行静态检查、单元测试、构建、契约校验、真实 PostgreSQL 测试及显式选择的外部集成测试。未启动的依赖导致对应测试阻塞，不把跳过算作通过。

三库各自验证快照期间变更、增删改、主键变化、乱序重复、故障恢复、日志过期和结构变化。API 验证分页中断、水位、幂等及删除语义。两路输出分别故障注入并核对。授权覆盖跨部门、自批、字段越权、到期和即时撤权；前端覆盖旧响应、失败空态和轮询生命周期。

每项证据记录版本、环境、输入、步骤、预期、实际和结论。备份恢复至少涵盖平台 PostgreSQL、Flink 恢复状态、Connect 位点及归档清单，验证容器重建后恢复，而非只验证进程重启。

用户补充要求新增以下验收项，作为 AT-15—AT-17、AT-19、AT-24 的扩展，不修改原文编号：

| 补充编号 | 验收内容 |
| --- | --- |
| FLOW-01 | 从共享交换原始接入开始，经治理、资产登记发布，回到共享交换完成治理成果交付；原始对象与治理数据集的血缘、版本、权限和状态一致，全程可审计 |
| FLOW-02 | 注入治理质量阻断、对应范围归档缺口、治理数据集下架和授权撤销，各平台展示对应原因，治理成果交付接口独立拒绝受影响的新查询；原始交换按其独立契约和授权判定，恢复前完成核对与批准 |
