# 数据治理融合设计：围绕治理空间完成任务与交付成果

日期：2026-10-23。状态：待用户审阅；当前只形成设计，未修改业务代码、数据库或主环境。

## 一、目标和已确认约束

用户需要用较少概念和操作，独立完成一次完整的数据治理：认识来源、处理数据、检查质量、产出和管理成果。保留元数据版本、常用字段标准、结果模型、图形与代码处理、工作流、定时、日志、质量、血缘及成果管理。每个场景在独立空间内工作。

默认页面展示当前业务对象、状态、结果和可执行动作。教学指南通过帮助入口主动打开，首次引导可跳过、可重看，不作为进入平台的前置条件。业务用途、字段含义和数据范围属于对象本身；专业字段只在旁侧提供简短解释。

不使用子代理、不采用红绿测试流程、不新增框架或绘图库。沿用 React、Ant Design、React Flow、CodeMirror 和现有 Go 服务。数据流继续使用独立页面；页面位置由面包屑表达，不恢复重复页面大标题。其他简短编辑沿用单层 dialog，命令统一右下角。

## 二、融合哪些能力

| 参考产品 | 本系统采用的组织方式 | 具体落点 |
| --- | --- | --- |
| Dataiku | 项目容纳一项工作，数据和处理关系直观可见 | 治理空间、可视化/代码共用处理链、对象内预览与质量 |
| DataWorks | 任务关联编排、自动执行及运维 | 任务详情内设置定时、查看本次日志和成果；多个任务有依赖时使用工作流 |
| Microsoft Purview | 按业务用途理解和组织可交付数据 | 成果展示用途、覆盖范围、字段、质量和使用方式；允许一个空间产生多份成果 |
| Collibra | 围绕资产汇集理解与使用所需信息 | 同一成果内查看结构、质量、来源、版本、责任和共享办理关系 |

这些是产品组织方式的借鉴，不引入新的外部平台依赖，也不承诺仅建立项目目录就实现执行环境隔离。

## 三、改造方式及取舍

选择“在现有执行和授权体系上增加空间边界，再调整交互”的方式。可以逐步验证隔离和历史兼容，继续复用已跑通的真实执行、质量、代码隔离及成果证据。

只调整导航和页面归类可以较快减少菜单，但无法满足独立场景要求。另建一套治理引擎会导致两套版本、运行和成果机制，增加迁移及维护成本。因此两者不作为本次方案。

## 四、导航与页面职责

平台层保持少量入口：

- 治理空间：日常工作入口，显示最近工作、最近运行、问题和成果，可新建空间。
- 元数据：复用共享交换接入的来源，查看结构、观察版本及当前结构差异。
- 公共标准：按需维护类型、格式、枚举值含义和字段规则。
- 全部成果：在既有权限内检索和使用各空间的治理结果。

进入空间后分别提供：概览、来源、模型、开发与编排、数据质量、成果、血缘记录。来源列表是本空间显式使用资源的集合；不会复制连接凭据，也不要求重新接入数据。

空间概览默认展示来源数量、最近运行、质量摘要和近期成果，提供“继续编辑”“查看成果”“查看问题”“设置定时”等与当前状态匹配的动作。无运行时展示实际空状态，不显示虚构得分或要求用户先学习概念。全局看板可保留为次级汇总视图。

开发与编排保留数据流和工作流的独立编辑页面。数据流负责数据处理；工作流在存在多个任务的依赖、分支和协同时使用。运行记录、日志及定时配置从对应任务直接进入，不要求跨菜单重新选择任务。

成果页面默认展示名称、用途、业务范围、生成时间、所属空间、质量摘要和使用状态。详情按概览、数据预览与字段、质量、来源与运行、版本和使用方式分区，保留按权限办理发布、共享和管理操作。

## 五、标准、元数据、模型和质量的关系

- 元数据来自实际接入资源及其结构观察。历史结构版本用于对比和追溯，不冒充源库回滚；文件/API的登记结构与实际读取结果明确区分。
- 公共标准按需引用。标准说明预期类型、格式、范围和码值含义，不强制每个字段都先建标准。
- 空间模型表达输出字段及业务范围，优先从来源或处理输出带入字段后确认。概念/逻辑/物理层级、建表和关系维护放入高级配置，不要求每次依次建立。
- 质量随实际数据对象和运行查看；可复用引用标准生成的检查，并允许警告和阻断两类结果。规则模板、趋势和整改合并为质量中的按需能力，不强制登记工单。
- 同一成果、同一规则依据的有效检查结果直接展示。规则或成果变化后重新检查；权限与使用条件仍在相应操作时复核。
- 血缘尽量从真实处理、输入及成果自动形成。外部处理允许补充说明，并明确标记为人工记录。

主题域与责任、业务术语不再作为普通用户的必经功能。业务范围并入空间和模型，责任人默认当前有效治理人员，字段含义保留在数据旁。已有主题域、术语和引用版本继续保留，可在高级信息或公共资料中访问。

## 六、治理空间的边界

新建空间只要求名称，允许补充用途；责任人默认创建人。沿用当前部门、角色和数据授权，不另建一套必须配置的成员审批体系。

### 6.1 配置和数据归属

每个空间有独立且不可混淆的标识。新建模型、数据流、工作流、私有质量模板均有唯一空间归属。输入资源和公共标准可以复用，但复用不授予新的读取、加工或共享权限。

运行、预览、任务实例、日志、调度和自动生成的成果继承所属任务的空间；中间数据继续按实际运行隔离，不能仅根据页面筛选判断隔离成立。数据库读写均验证空间归属和原有权限，服务端阻止伪造空间参数或跨空间修改。

### 6.2 跨空间复用

普通处理只能选择本空间定义。需要复用其他空间的处理时复制为本空间独立定义，不修改原对象；复制时对模型、模板和任务依赖一并核对，不保留隐蔽的可变共享引用。

跨空间读取成果是显式操作：选择已获准使用的具体成果及其固定版本，保留上下游关系。公共标准复用固定有效版本，升级需明确选择。复用不会自动继承提供方的连接凭据或扩大敏感字段范围。

### 6.3 运行与生命周期

新增空间并发限额和现有用户/全局预算共同生效，保留代码执行的既有安全隔离。首轮提供配置、临时数据和调度隔离以及资源限额；共享基础设施下不承诺零性能影响，也不为每个空间默认创建整套数据库和容器集群。

空间归档只停止本空间后续调度及新编辑；不删除来源数据，不取消其他空间运行。归档时列出在途运行，需明确取消或等待后再完成归档。已被下游使用的成果继续按现有依赖和保留规则保护。首轮不提供一键物理删除空间。

## 七、简化操作，但保留可重现执行

用户的主线是：创建空间 → 选择来源 → 编排和试运行 → 生成并检查成果 → 按需定时或发布共享。

保存配置自动保留版本；正式执行固定使用的一整套配置和依赖，后续修改不改变历史证据。界面不再要求用户逐个菜单发布内部定义，但不能通过隐藏按钮绕过现有后台校验。

当前实现要求引用已发布模型，数据流/工作流运行也要求定义已发布；调度仅引用工作流。简化这些环节需分别提供明确的后台事务接口：

1. “保存并运行”先校验和生成可执行的固定配置快照，再排队运行。引用冲突或权限不足时不产生假成功，不把共享定义自动发布为当前草稿。
2. 单条数据流可以直接定时，调度直接固定其版本；多任务调度继续引用工作流。用户不用为单个任务手工创建空壳工作流。
3. “发布共享”是成果对外使用的动作，与内部配置固定分开。完整性、质量、当前权限及已配置的使用条件继续在后台核对。

上述后台行为作为后续独立交付；在完成之前明确保留原有执行约束，不用前端文案提前宣称已简化。

## 八、兼容现有数据

- 保留现有定义编号、历史版本、运行编号、成果内容、证据、已发布状态和共享引用。
- 按原部门建立“历史治理”空间，承接已有模型、数据流和工作流；可明确追溯的运行和成果随原任务归入该空间。历史外部成果保留原来的登记路径和权限，不伪造成自动产出。
- 公共标准、主题域、术语及共享交换来源保留原记录。已有跨对象关系在迁移报告中列明，不自动拆分成未经确认的新业务场景。
- 存量调度不因界面改造自动启停或切换版本。新空间执行新边界规则；迁移期历史空间保持原有引用关系，不能将其宣传成已全部隔离的独立场景。
- 未归属或归属有歧义的记录留在历史范围并明确标识，不按名称猜测业务归属。
- 旧链接继续定位对应对象并显示所属空间；旧 API 保持兼容。新空间上下文必须由服务端核实，缺失上下文的旧请求只走受控的历史兼容路径。
- 数据库采用可前向兼容的新增字段、关联和索引；部署前备份恢复演练，明确新增数据后旧版服务的写入边界，避免仅有旧镜像却无法安全回退。

## 九、交付顺序和验收

### 首轮：空间基础与工作入口

完成空间归属、服务端隔离、历史归档映射、上下文导航及空间概览。已有真实模型、处理、质量、成果和血缘从空间进入；默认移除常驻教学长文，但保留主动帮助。已有执行发布约束先沿用，不声称全部交互已简化。

验收：新建客户和商品两个空间，分别建立任务；客户空间的配置修改、取消运行和调度变更不影响商品空间。越权、伪造空间、跨空间写入被拒绝。历史客户治理流及旧链接仍可查看和运行；源数据和原成果内容不变。

### 第二轮：处理工作区与自动运行

完成保存并运行的固定快照、字段带入和模型便捷生成、数据流直接定时、就地日志及问题定位。代码和拖拽编排继续复用现有执行方式。

验收：用户无需先建立主题域/术语，无需为单条数据流创建工作流，即可从有效来源完成处理、运行、看日志并开启定时；执行失败可定位到实际节点和安全诊断。

### 第三轮：成果交付与质量整合

完善成果用途、范围、预览、质量、版本、血缘和共享入口，合并质量、生命周期等分散入口。复用真实有效报告，移除重复手动检查。治理空间可以产生多份成果，不强制一空间一张表。

验收：关闭全部教学引导后，用户仍能独立完成客户资料整理并找到成果、理解字段和质量、办理有权共享。无法发布时说明具体缺项及解决入口，不要求学习概念才能继续。

各轮实施后运行对应的构建、类型检查、必要的回归和真实流程验证，不采用测试先行红绿流程，不使用子代理。主环境部署沿用备份、严格证书校验、接口和静态资源核对，以及现有数据指纹对比。

## 十、现有代码核对依据

- `web/src/app/App.tsx`：治理目前有 19 个独立页面入口。
- `internal/modules/workflow/governance_catalog_http.go`：定义头按部门归属；依赖验证、版本和发布逻辑集中在现有实现。
- `internal/modules/workflow/governance_dataflow_http.go`：运行固定依赖和输入，要求已发布定义，现有并发限制按用户。
- `internal/modules/workflow/governance_schedule.go`：调度当前固定引用工作流，尚无直接数据流调度。
- `internal/modules/workflow/governance_outputs.go`：成功运行生成治理成果和不可修改的产出证据。
- `internal/modules/workflow/governance_operations.go`：运行、质量、血缘汇总需增加真实空间范围校验。
- `web/src/pages/GovernanceDataflows.tsx`：复用已部署的独立画布、代码配置、版本、前置核对和运行结果。
- `web/src/pages/GovernanceResults.tsx`：复用当前成果核验与共享办理能力，调整默认呈现和信息分区。
