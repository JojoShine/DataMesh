## 测试条件

- 开发机：Apple M1 / arm64，Docker Linux容器。执行进程限制2 CPU、512 MiB，GOMAXPROCS=2、GOMEMLIMIT=384 MiB。
- 两个独立PostgreSQL容器：来源容器256 MiB，目标容器384 MiB；数据库版本均为PostgreSQL17.11。目标兼作平台元数据数据库，不是专用生产集群。
- 使用两个新建的独立测试库。数据经过真实HTTPS任务提交、持久队列、权限检查、应用流式读取/转换、多行upsert及目标事务提交；没有用数据库内部INSERT SELECT代替交换。
- 100万行、6个字段：bigint主键、客户名称、邮箱、numeric(20,6)金额、timestamp(3)、128字符备注。名称执行trim，邮箱转小写，其他字段直接映射。
- 来源表及主键索引占用 244.74 MiB；执行器估算转换后逻辑数据 223.90 MiB。后者不是网络抓包字节量。
- 每批最多500行/4 MiB，本次每轮2000个实际SQL写入批次；目标整轮单事务。PG每批savepoint保护数据库主键归一化回退，不做分段提交。
- 未清空操作系统或数据库缓存，测试机并非独占生产环境；三次不是冷启动基准，也不足以推导长期SLA。

## 计时与正确性

业务计时从HTTPS提交运行前开始，到查询观察到succeeded结束，包含排队、读取、转换、写入、提交和最多约100ms的观察延迟。worker执行时间来自运行记录的started_at/finished_at，单独列出。数据准备、登录、清空目标以及同步完成后的核对不计入同步时间。

每次核对目标总行数、主键唯一/范围，并逐行检查名称、邮箱、精确小数、时间及备注是否与合成来源的转换结果一致；四次均为100万行、0个字段不匹配。已有主键更新后仍只有100万行。

执行进程生命周期的峰值RSS：**46.36 MiB**（Linux VmHWM，包含测试服务、客户端及准备/核对阶段）。运行期间按约100ms采样的Go堆峰值最高为 12.21 MiB，并非严格的瞬时堆峰值。

## 本轮补齐的能力与回归

- HTTP只负责保存运行请求；持久queued记录由worker领取。无worker时保留排队，重建worker后继续处理，等待不占执行时限。
- 数据库租约和心跳、全局ETL配额2、新执行器启动不重置已有有效租约；失联/失租约进入unknown，保留目标占用，禁止自动重放。
- 元数据目标占用加目标数据库锁，约束本平台ETL的同目标并行。为防止连接别名绕过unknown，保守按库名/schema/表名跨主机串行；不同物理库同名也会串行。
- 直接库表改为只读一致性快照流式读取、参数化多行写入、限量缓冲。默认上限200万行/1 GiB/30分钟；PG/MySQL都保留整轮目标事务。
- PostgreSQL/MySQL四种交换组合各1501行跨批回归，含大于JavaScript安全整数范围的主键与精确小数。数据库char主键等价时savepoint回退顺序写入；小数精度或范围缩窄会被拒绝。
- 真实故障回归：日志保存失败、跨批约束失败、取消、活跃worker丢租约均不得产生已确认失败后的目标交付；回滚结果不明则保留unknown，核实前检查目标事务锁。目标互斥及告警处理继续验证。

## 适用边界

这个结果证明当前代码在上述本机环境能正确完成百万行直接库表交换，不能等同于远程网络、任意字段类型/宽度或长期高并发的性能承诺。MySQL四组合通过功能回归，但本次百万行性能测试仅为PG→PG。

平台资源/归档/治理成果继续复用原授权、脱敏、质量读取通道及1万行/20 MiB边界，没有为了跑分绕过它们。超大单字段、日期时区跨类型、数据库故障切换及生产负载仍须按实际场景独立验收。

目标整轮单事务仍会持有锁并产生WAL；成功的处理行数不是新增唯一记录数或业务验收回执。提交前租约检查与外部Commit不是分布式原子操作；越过提交边界后失联仍须unknown和人工核实。持久排队不是断点续传，尚未实现自动增量、检查点续传、重试退避、调度和正式交付回执。整个平台多实例高可用不在本轮验收范围。
