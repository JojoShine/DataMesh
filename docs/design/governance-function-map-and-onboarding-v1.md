# 数据治理功能关系、菜单与学习引导方案 V1

日期：2026-10-22  
状态：基础功能关系与菜单方向已确认；本次补充成熟平台交互参考，供后续页面设计采用；尚未实施。  
范围：完整保留现有治理功能、版本、校验、授权、审批和证据链，优化功能分工、解释和前后衔接。此方案替代此前“将全部整理发布步骤集中到一个长 Dialog”的交互方向。

## 1. 设计目标与判定口径

用户应能在每个功能中回答：为什么需要它、什么时候用、开始前准备什么、完成后得到什么、哪些功能会继续使用它。

三类标识必须相对于具体业务目标解释：

- **必选**：完成当前目标必须具备的条件或必须通过的校验；已存在且有效的对象可以复用，不要求重复新建。
- **条件必选**：进入相应场景或选择相应能力后，就必须完成。界面应直接写明触发条件。
- **可选**：按当前业务需要使用；跳过会失去哪种管理或分析能力，也应说明。
- **自动留痕**：系统随真实操作生成的版本、运行和血缘等证据。生成不可省略，用户是否主动查看按场景决定。

“可选”表示该业务场景可能不适用，不表示删除功能或忽略现有校验。“管理上建议使用”不冒充“当前系统已强制要求”。如将来组织制度要求所有模型归属主题域，应明确作为新的业务规则另行确认。

本表基于现有前后端实现核对。当前定义要求填写责任人、维护人，主题域、标准和术语关联并非所有定义的强制前置。来源权限沿用现有角色、资源能力、加工授权及管理员处理规则，学习进度不改变任何权限。

## 2. 菜单划分建议

工作台独立，其余按职责分组，最多两级。菜单回答“我要在哪里完成哪类工作”，页内标签回答“同一对象有哪些信息”。

| 分组 | 二级菜单 | 内容和边界 |
|---|---|---|
| 治理工作台 | 独立入口 | 业务关系总览、我的待办、近期工作、学习入口；统计作为辅助信息 |
| 业务规范 | 主题域与责任 | 管理业务范围及定义责任；责任字段继续在各定义中填写，复用已有人员体系，不另造人员管理系统 |
| 业务规范 | 数据标准 | 从现有“标准与术语”中拆出；管理技术约束、允许值和标准版本 |
| 业务规范 | 业务术语 | 从现有“标准与术语”中拆出；管理业务含义和适用边界 |
| 数据认知与建模 | 元数据管理 | 来源列表；详情按“结构与变化 / 业务注释 / 输入要求”切换，文件结构化契约和 API 参数说明放在对应来源中 |
| 数据认知与建模 | 数据剖析 | 独立入口选来源、字段和观察范围，查看剖析历史；从元数据进入时自动带入来源，复用同一剖析能力 |
| 数据认知与建模 | 数据建模 | 概念、逻辑、物理模型；详情包含字段、约束、关系、版本；目标建表及 DDL 预览仍依附具体物理模型 |
| 开发与调度 | 数据流开发 | 管理、设计、发布数据处理步骤；画布与当前节点配置并排，避免全部节点表单纵向展开 |
| 开发与调度 | 工作流编排 | 从原“工作流与调度”拆出，管理任务依赖、执行条件及版本 |
| 开发与调度 | 调度计划 | 从原“工作流与调度”拆出，管理自动触发规则、启停和触发记录 |
| 数据质量 | 历史成果质量规则 | 现有“质量规则”的说明性名称调整，明确用于历史成果登记路径，完整保留规则功能 |
| 数据质量 | 数据流质量模板 | 现有“质量模板”的说明性名称调整，说明由数据流质量节点引用 |
| 数据质量 | 成果质量检查 | 汇总成果质量与完整性门禁；可定位对应来源、运行及结果绑定 |
| 数据质量 | 质量趋势 | 观察历次检查变化，跳转相关运行和问题 |
| 数据质量 | 质量整改 | 登记、分派、处理、复测和关闭问题 |
| 运行与追溯 | 运行运维 | 统一查看剖析、数据流、工作流的真实运行；各业务入口带条件进入同一记录 |
| 运行与追溯 | 血缘与影响 | 页内区分来源追溯、变更影响；两者共享对象关系，保留全部分析能力 |
| 运行与追溯 | 治理告警 | 规则配置和告警记录两个标签，独立处理通知与异常发现 |
| 成果与生命周期 | 治理成果 | 汇总成果及来源、模型、运行、质量和发布状态，作为后续工作的对象入口 |
| 成果与生命周期 | 成果发布 | 对接现有数据资产发布能力，按权限进入同一发布办理页面和 Dialog，不另建第二套发布记录 |
| 成果与生命周期 | 发布审批 | 对接现有工作流成果审批，单独入口显示待审批事项；与普通成果直接发布明确区分 |
| 成果与生命周期 | 保留与清理 | 从现有生命周期拆出，保留策略和清理预检分别展示 |
| 成果与生命周期 | 下游迁移 | 从现有生命周期拆出，独立管理新旧成果替换、迁移草稿及完成核验 |

菜单拆分属于本方案拟调整项，不能将此表当成当前已上线菜单。跨平台入口遵守原有平台和角色权限；没有办理权限时说明需要哪个职责，不提供无权操作。

### 2.1 页面与 Dialog 的组织

- 列表用于寻找对象、了解当前状态；新建、编辑、核对、发布和审批采用单层 Dialog。
- 同一对象的不同视角用标签或内容切换；更换 Dialog 内容时提供返回入口并保留上下文，不叠加第二层普通操作弹窗。
- 标题、必要步骤导航和右下角底栏固定；只滚动中间内容。上下页、取消、保存、检查、运行、发布等命令都在右下角，间距16px，窄屏靠右换行。
- 数据流设计：画布、节点属性、结果/诊断按区域切换；高级配置按节点展开。工作流设计：任务依赖与当前任务属性分区。调度独立办理，不接在编排页面下方形成长页面。
- 版本、运行、质量和成果之间按真实引用关系跳转，自动带入名称、编号及版本；返回后保留原选择和填写状态。
- 主题域、标准、术语、模型、数据流等各自的草稿、发布、修订、迁移说明、停用和历史查看能力全部保留。跨功能衔接只带入上下文，不代替业务核对。

## 3. 完整功能关系表

### 3.1 业务规范与责任

| 功能 | 必要性与适用场景 | 前置条件 | 产生的结果及后续关系 | 必选/可选判定 |
|---|---|---|---|---|
| 主题域 | 划定客户、订单、财务等业务边界，便于分类、查找和跨团队协作；多业务域建设尤其需要 | 明确业务范围、部门及负责人员 | 发布的主题域可被标准、模型、数据流等支持关联的定义引用，业务注释亦可归属主题域 | **可选**，当前不是单条数据流的强制条件；需要关联时所引用版本须已发布。组织统一分类建议纳入建设规范 |
| 责任人、维护人 | 让定义及变更有承接人，使用者知道应找谁确认含义、谁维护内容 | 本部门符合条件的有效人员及真实分工 | 各定义保留责任信息，供协作、解释和维护使用；具体审批及访问权仍按已有权限规则 | **必选**，适用于现有治理定义；填写责任不等于自动授予账号权限，也不自动产生审批链 |
| 数据标准 | 统一字段的类型、长度、精度、空值、敏感范围、格式或允许值；跨系统口径不一时使用 | 明确技术编码、字段规则及业务依据；如关联主题域先有已发布版本 | 模型字段、业务注释可引用；码表转换可使用标准允许值。数据是否按规则处理，需看模型引用和处理配置 | **可选**；一旦引用标准，该版本及适用约束为**条件必选**。单独建立标准不会自动清洗或批量治理来源 |
| 业务术语 | 统一“有效客户”“订单金额”等概念的含义和适用边界，减少同名不同义 | 经业务确认的定义、责任人员 | 发布后关联到元数据字段业务注释，帮助业务人员理解和使用字段 | **可选**；需要术语关联时引用已发布版本。术语说明本身不执行客户筛选或金额计算 |

### 3.2 数据认识、输入与建模

| 功能 | 必要性与适用场景 | 前置条件 | 产生的结果及后续关系 | 必选/可选判定 |
|---|---|---|---|---|
| 来源结构与契约核对 | 认清真实来源及字段结构，防止同名对象、字段类型、精度或契约版本选错 | 已接入且当前账号可见的资源；读取真实结构还需对应来源可用 | 明确后续读取字段和版本；不兼容变更回到资源维护处理，再更新模型和数据流引用 | 结构依据正确是**必选**；单独生成一次新的观察记录按需要，不将“点过某按钮”当成业务正确的证明 |
| 结构观察与变更历史 | 保存结构在何时发生何种变化，定位运行失败或评估修改影响 | 可观察的来源；数据库读取实际结构，其他类型按现有登记契约能力处理 | 形成观察快照和差异供注释、变更判断及排查引用；不自动修改资源契约 | **可选**；需要登记业务注释时，所关联结构观察为**条件必选** |
| 元数据业务注释 | 把技术字段解释成可理解的业务含义，关联标准、术语 | 已有结构观察；责任人员；被关联的标准、术语须已发布 | 形成可发布、可追踪版本的注释，供业务理解和后续治理查看 | **可选**；对面向非数据人员提供的成果，建议作为交付说明要求，不冒充现有系统强制规则 |
| CSV/XLSX结构化输入契约 | 将文件字段和类型固定下来，使文件可以参与按行剖析、治理计算 | 已登记的受支持文件、维护权限、与文件表头和类型匹配的已发布模型；指定工作表及表头行 | 完整文件核验后产生新资源契约版本；后续须核对挂接、字段授权和数据流引用 | 文件参加结构化治理时为**条件必选**；PDF等非结构化文档不被误导为可按行治理 |
| API输入与参数 | 说明本次读取哪个受控接口、允许填写哪些业务查询条件 | 已接入接口、声明的输入字段与查询参数、有效权限 | 成为数据流来源；运行时可使用已声明参数或参数绑定 | 使用API来源时为**条件必选**；必填参数必须填写，不让业务用户填写目标凭据或任意请求内容 |
| 数据剖析 | 观察空值、重复、分布和范围，辅助判断数据问题及制定规则 | 结构化可读取来源、所选字段加工权限，文件/API各自的输入条件 | 产生采样或全量观察报告；用于标准、模型及质量检查配置，也可供问题定位 | **可选**；未知来源或质量情况不清时建议先做。采样通过不能代替完整运行或发布门禁 |
| 概念模型 | 先说明业务对象和关系，帮助业务与建设人员达成一致 | 明确业务对象、责任及范围 | 为逻辑、物理模型设计提供依据；不会自动转换成可执行结果字段 | **可选**，适合业务规划；不强迫每个现成来源都先建概念模型 |
| 逻辑模型与输出要求 | 约定结果字段、类型、主键、敏感范围、质量容忍度、鲜度及使用约束 | 明确结果用途和字段要求；引用的标准、关联模型已发布 | 已发布且含可执行字段的模型可被数据流输出节点或文件契约固定引用 | 对生成数据流成果，**可执行的已发布输出模型必选**，可以复用；逻辑/物理层按用途选择，无须三个层级逐个新建 |
| 物理模型、实体关系 | 进一步规定目标Schema、表名、主键及模型间的关联 | 目标设计、字段与关联模型已明确；物理模型须满足非空主键等现有约束 | 为目标建表和关系查看提供依据，也可按现有规则作为输出模型 | 选用物理模型落地时其结构约束为**条件必选**；实体关系按业务**可选**，建表不强迫配置实体关系，也不自动创建数据库外键 |
| DDL预览与目标建表 | 核对将要创建的结构，并按需要在真实数据库创建新空表 | 预览需适用模型；实际建表需已发布物理模型、存在的Schema、目标权限、预检通过且表不存在 | 留下预览、执行和核对回执；需要写入数据时再办理共享交换数据同步 | 实际建新表时**条件必选**；生成治理成果并不要求额外建一张外部表；建表不自动写入数据 |

### 3.3 开发、编排与调度

| 功能 | 必要性与适用场景 | 前置条件 | 产生的结果及后续关系 | 必选/可选判定 |
|---|---|---|---|---|
| 数据流开发 | 明确一份或多份授权数据如何经过读取、转换和检查，形成符合模型的结果 | 有效来源、字段和派生成果所需加工权限；可用输出模型；各处理节点配置合法 | 保存、发布固定版本后可手动运行，也可被工作流引用；成功运行产生真实治理成果 | 通过本平台加工生成新成果时**必选**；历史已有结果可以走独立登记路径，不伪造一次新加工 |
| 运行参数 | 在固定处理逻辑下改变本次日期、筛选值或API业务条件，避免反复改定义 | 数据流/工作流先声明支持的参数和类型；当前值符合要求 | 本次运行保留明确参数，调度可固定参数；不改变未声明的处理逻辑 | 配置参数化条件时为**条件必选**，无参数的流程不强迫填写 |
| 工作流编排 | 组织任务依赖、执行条件、质量核验和发布审批等环节；需要有顺序或条件的处理时使用 | 被引用的数据流等对象已发布且可用；前置成果与任务输入关系合法 | 发布的工作流可手动执行或交给调度；记录各任务和子运行结果 | 需要任务依赖、条件分支或工作流发布审批时**条件必选**；独立数据流可单独运行 |
| 工作流质量核验任务 | 在编排中设置明确的核验环节，让后续任务按检查结论执行 | 前置任务提供有效成果；阈值及依赖关系明确 | 留下独立核验结果，为后续任务或发布审批提供依赖 | 采用这类编排门禁时**条件必选**；不代替数据流内部检查，也不取消最终发布校验 |
| 调度计划与触发记录 | 按固定间隔或日历自动触发工作流，解释何时执行、跳过或失败 | 有可运行的已发布工作流、有效执行身份；首次时间、时区和错过触发策略明确 | 形成调度、触发及运行记录；工作流新版本不自动替换已有调度 | 需要定时自动运行时**条件必选**；先手动跑通属于操作建议，应区别于后端已强制校验的条件 |
| 版本、修订、发布与停用 | 保证结果可复现，防止修改影响正在使用的定义；供持续迭代和变更管理 | 已有对象及对应维护权限；发布满足引用约束；破坏性变更按现有规则填写迁移说明 | 新版本供后续明确引用，旧版本和历史证据保留；被依赖版本的停用受阻断 | 对使用固定版本的处理是**必选机制**；是否修订、停用按场景，不能由学习引导跳过 |

#### 数据流算子关系：保留全部能力

| 算子 | 为什么使用 | 输入与后续关系 | 判定 |
|---|---|---|---|
| 数据来源 | 指定读取哪份授权数据及哪些字段 | 输出字段进入后续节点，保留资源契约版本 | **必选**，至少一个有效来源 |
| 字段投影 | 选择字段、调整输出名称 | 输入已有字段，输出供后续计算或模型匹配 | **可选** |
| 文本转换 | 去除首尾空白、统一大小写 | 输入适用的文本字段，输出清洗后的字段 | **可选** |
| 数据筛选 | 按业务条件保留记录 | 需要合法字段、比较类型及值；输出行进入后续处理 | **可选** |
| 记录去重 | 按明确业务键保留记录，减少重复 | 需要可用去重键；不能把敏感脱敏键当成可靠原始键 | **可选** |
| 多表关联 | 将不同来源按关联键组合 | 两侧输入和兼容关联键；输出参与后续处理，受数据量边界约束 | **可选** |
| 分组汇总 | 按业务维度计算计数、求和等结果 | 分组字段、适用汇总字段及运算；结果匹配汇总模型 | **可选** |
| 质量分流 | 按检查条件识别异常，合格与不合格分别处理 | 逐项检查或固定模板；跨表检查需第二输入；成果输出连接允许的合格分支 | 需要显式业务检查和分流时**条件必选**；当前实现不强制每条数据流都加该节点，但输出模型约束仍执行 |
| 码表映射 | 将来源编码转换成统一标准值 | 已发布标准、原值与标准值映射、未匹配处理方式 | 使用码值转换时**条件必选** |
| 模型输出 | 将最终字段核对为明确的结果要求 | 字段与已发布模型相容；完整执行成功后登记成果 | **必选** |

### 3.4 质量与整改

| 功能 | 必要性与适用场景 | 前置条件 | 产生的结果及后续关系 | 必选/可选判定 |
|---|---|---|---|---|
| 历史成果质量规则 | 为历史结果登记路径约定应检查的来源字段和规则 | 明确来源、字段、检查类型、参数及阻断属性 | 已发布规则在历史成果登记时固定绑定，不自动覆盖既有成果 | 选择历史成果登记路径时**条件必选**；不要求新数据流再走一次历史规则登记 |
| 数据流质量模板 | 复用一组相同字段及检查，避免多条数据流反复配置 | 已确定字段和类型；跨表检查具备参考字段；模板须发布后引用 | 被质量节点固定版本引用；模板升级需明确更新数据流引用 | **可选**；使用模板方式配置质量节点时为**条件必选**，逐项检查仍完整保留 |
| 成果质量与完整性门禁 | 确认成果有真实、有效的处理证据，满足质量及完整性要求 | 已产生或登记真实成果；自动成果依据实际运行，历史成果依据绑定核验 | 显示质量、完整性、范围及阻断原因，供发布、使用和排查核验 | 成果发布必须通过门禁，属于**必选**；独立点击“重新检查”按需，发布仍会重新核验证据 |
| 质量趋势 | 发现质量是否随时间变好或恶化，定位反复出现的异常 | 数据流已有质量检查事件；时间范围和时区明确 | 形成检查与隔离趋势，可定位相关运行并发起整改 | **可选**；检查行次不冒充唯一数据行数，没有事件时解释暂无趋势 |
| 质量整改 | 将真实异常交给具体人员处理，以复测证明问题闭环 | 存在真实质量失败或隔离运行，明确责任人、期限和处理记录 | 同一数据流版本复测成功且无隔离后核验关闭；历史完整保留，未关闭问题影响成果清理 | 决定登记并管理问题时为**条件必选闭环**；不是所有来源或运行都要预先新建整改问题 |

### 3.5 运行、血缘与告警

| 功能 | 必要性与适用场景 | 前置条件 | 产生的结果及后续关系 | 必选/可选判定 |
|---|---|---|---|---|
| 运行记录与诊断 | 确认实际执行到哪里、处理多少数据、为什么失败；避免把定义发布误当成执行完成 | 已发起剖析、数据流或工作流运行；有相应可见权限 | 真实状态、日志、计数和成果证据，供质量、发布、追溯及排查使用 | **自动留痕**；产生新成果必须有成功运行，主动查看各类日志按场景 |
| 取消、重试与恢复 | 在失败或中断后有依据地继续工作，避免盲目重复或混用快照 | 符合操作条件的运行；先处理来源、授权或配置问题 | 取消留痕；重跑建立新运行；工作流恢复重新核验可复用成果 | 异常处理时**条件必选**；不同运行的数据不拼装为同一次结果 |
| 字段血缘与来源追溯 | 解释结果来自哪里、经过哪些处理，支持复核和可信使用 | 已有相应运行或登记关系，且当前账号可见 | 输出来源、处理和版本关系，可回到原对象或运行查看 | 证据随真实处理**自动生成**；主动追溯按场景，不要求用户另手工造一份血缘 |
| 变更影响分析 | 修改、停用或迁移之前识别被谁使用，减少下游故障 | 可识别的来源、资源、定义、运行或成果；依赖关系可见 | 实际已登记依赖和受限范围提示，为迁移和停用决策提供依据 | 主动查看为**可选**，改动在用对象前强烈建议核对；处理实际阻断依赖为**条件必选**，不以“看过图”替代执行校验 |
| 治理告警 | 主动发现运行失败、中断或质量隔离超阈值，避免只能手动查运行 | 明确条件并启用规则；外部通知使用获准目标 | 告警记录指向真实运行；跟踪通知状态和重试；再进入运行或整改处理 | **可选**；常态自动运行建议配置。设置告警不自动修复问题 |

### 3.6 成果发布、使用与生命周期

| 功能 | 必要性与适用场景 | 前置条件 | 产生的结果及后续关系 | 必选/可选判定 |
|---|---|---|---|---|
| 自动成果登记与成果查看 | 将成功运行形成的结果与来源、模型和质量证据关联，供后续识别、发布和使用 | 数据流成功产出符合要求的结果 | 自动登记成果及快照证据，可从原运行直接进入；查看字段、状态、质量和完整性 | 自动登记为该路径的**必选机制**；不得要求用户再手工登记一次同样成果 |
| 历史治理成果登记 | 将平台外已形成的历史结果纳入契约及核验管理 | 对应职责和权限；来源已发布质量规则，符合现有登记字段要求 | 建立固定规则和字段契约，之后必须绑定真实结果并核验 | 采用历史结果路径时**条件必选**；登记不会自动生成或复制结果数据 |
| 历史结果库表绑定与完整范围核验 | 证明登记的历史结果确实对应原始归档及转换，而非仅有说明 | 已登记历史成果、可用的完整原始归档、实际目标库表、正确映射及权限 | 核验通过后形成固定结果快照，进入质量门禁和发布 | 历史结果路径为**条件必选**；自动数据流成果已有真实运行证据，走自身核验机制 |
| 普通成果核验发布 | 将已核验成果发布到数据资产，供后续共享编目 | 实际成果、维护及发布职责；质量、完整性、来源授权、鲜度等满足当前校验 | 产生已发布状态，后续办理共享目录、挂接和授权；不会自动公开或授予访问 | 需要正式发布成果时**条件必选**；发布不是每次内部试运行都要执行 |
| 工作流成果发布审批 | 对工作流中要求审批的成果由有职责人员复核并决定是否发布 | 工作流实际进入待审批任务；成果证据有效；审批人满足现有职责及申请人与审批人的限制 | 批准则核验发布并推进工作流，驳回留理由；后续共享办理仍单独进行 | 配置发布审批任务时为**条件必选**；普通直接发布与此路径不是一律连续必经的两次发布 |
| 成果下架 | 停止继续以已发布成果提供后续使用 | 已发布成果及维护职责，满足对应操作校验 | 下架留痕；后续处理现有引用、迁移和保留安排 | 需要停止发布时**条件必选**；不等于删除历史证据 |
| 保留策略与快照清理 | 控制过期快照占用，同时保护在用和被依赖成果 | 有可管理成果；符合最短保留、发布/授权/整改/依赖保护；策略启用及清理执行各自确认 | 生成策略或清理回执；仅清理允许删除的行快照，保留相关定义、运行和证据 | **可选**；选择清理后全部预检与确认均为**必选**，到期不代表可强制删除在用数据 |
| 下游成果迁移 | 用新成果替换旧成果，并逐项处理依赖，防止直接替换破坏使用 | 同部门可用新旧成果、字段兼容、依赖信息及对应权限 | 形成迁移计划和新草稿；逐项办理定义、目录、授权等变更，核验无旧依赖后完成 | 替换在用成果时，核对并处理旧依赖为**条件必选**；使用此迁移工作台登记计划按需，不将计划登记冒充现有全局强制条件。审批和授权不自动复制，旧版本和证据保留 |

### 3.7 平台边界：前置与后置办理

这些能力继续在已有平台办理，治理入口负责解释关系并带入对象，不复制一套实现。

| 功能 | 为什么需要 / 场景 | 前置 | 后续 | 判定 |
|---|---|---|---|---|
| 数据源与资源接入（共享交换） | 让平台有可识别且可读取的真实数据 | 目标配置、连接及对应维护权限 | 治理元数据、文件/API输入、剖析和数据流读取 | 使用外部来源时**条件必选**，可以复用已接入资源；不能将每次治理解释为重做一次接入 |
| 资源维护、目录挂接与审核（共享交换） | 明确资源结构、目录归属及共享范围 | 对应资源和目录职责、材料及结构约束 | 支持共享、授权及资源维护；契约变动后按原规则更新范围 | 在相关挂接、共享和授权路径中**条件必选**；不把“每次源读取都先新建目录”列为全局条件 |
| 数据加工授权（共享交换） | 明确谁可读取哪些字段用于治理，以及是否允许派生成果 | 对应有效资源、授权范围、用途和期限 | 支持剖析和数据流；变更或失效可阻止后续执行 | 实际读取和派生成果必须满足现有有效权限依据，属于**必选条件**；与成果使用授权不同 |
| 成果共享目录、挂接、审核（共享交换） | 将已发布成果按目录、范围和条件对外提供申请 | 已发布且符合共享要求的成果、目录和相关材料 | 使用方发现并申请；获准后交付 | 需要共享时**条件必选**；发布到资产库不自动完成此流程 |
| 数据使用申请、审批与授权（共享交换/数据资产） | 限定消费者可使用的数据、字段、用途及期限 | 共享资源有效并完成对应申请审批 | 获准查询、下载或调用；不会反向授权消费者加工原始来源 | 使用需要授权的数据时**条件必选**；教学完成不能替代授权 |
| 数据同步（共享交换） | 将数据写入指定目标，区别于仅建空表或登记治理成果 | 来源、目标、映射、权限及适用核验 | 目标数据更新和相应执行记录 | 需要向外部目标落数据时**条件必选**；并非所有治理成果都要另做同步 |

## 4. 业务关系应怎样向用户展示

### 4.1 主线：加工并发布一份新成果

来源与有效权限 → 核对结构和业务目标 → 明确结果模型 → 配置并发布数据流 → 完整运行 → 核对成果质量/完整性 → 核验发布 → 按需办理共享与使用授权。

主题域、术语、标准支撑业务分类、口径和字段约束，按实际使用关系接入主线；已有有效定义可以复用，不强制重复建设。工作流、调度、告警、趋势、整改、血缘和生命周期按照各自触发条件衔接。

这条线用于说明工作关系和定位办理入口，各专业功能仍在职责明确的页面和 Dialog 完成，不将所有功能塞进一张长表单。

### 4.2 历史成果路径

已有来源及真实原始归档 → 发布历史成果质量规则 → 登记已有治理结果 → 绑定实际结果库表并完整核验 → 成果质量/完整性门禁 → 核验发布 → 按需共享。

这条路径与自动数据流产生成果并列；界面应先问清“新加工一份数据”还是“纳管已有结果”，避免混用两套质量配置。

### 4.3 自动化与异常分支

- 自动化：已发布数据流 → 工作流任务与依赖 → 发布工作流 → 建议先手动核验 → 配置调度 → 查看实际触发与运行 → 告警发现问题。
- 质量闭环：真实检查异常 → 登记并分派问题 → 修复原因并记录 → 原数据流版本复测 → 核验关闭。
- 变更闭环：识别变更目的 → 查看版本差异和下游影响 → 准备新版本/新成果 → 按需登记迁移 → 核验新运行 → 切换实际依赖和授权 → 核验迁移完成 → 按规则停用或清理旧对象。

### 4.4 容易混淆的状态必须说清

| 状态或操作 | 实际含义 | 后续仍需办理 |
|---|---|---|
| 标准或术语已发布 | 这份约定可被引用 | 关联或配置使用；不能声称数据已自动规范化 |
| 模型已发布 | 结果字段及要求的某版本可被引用 | 配置、发布并运行数据处理 |
| 数据流/工作流已发布 | 处理或编排定义可执行 | 发起运行；不能声称数据已生成 |
| 运行成功 | 此次执行真实完成 | 核对成果和适用门禁；按需发布 |
| 样本检查通过 | 对指定样本的观察完成 | 完整运行与正式门禁 |
| 成果已发布 | 成果可进入后续共享办理 | 目录、挂接、审批和使用授权 |
| 完成学习 | 用户看完相应教学主题 | 正式业务中的配置、权限、校验和审批仍须实际完成 |

## 5. 每个功能统一的解释方式

每页顶部保留简短“用途与关系”区，默认显示用途和当前最相关前置；完整说明按需展开，不让说明撑高页面。

固定内容：一句白话用途、适用场景、前置条件及实际状态、结果及后续关系、必选/条件必选/可选标签。点击条件可定位对象和对应办理入口。尚未核验的条件显示“待核验”，不靠用户点过“下一步”就标成通过。

主题域页面示例：

> **为什么需要：**把客户、订单、财务等数据归入明确业务范围，并让使用者找到相关负责人。  
> **什么时候用：**需要统一分类、跨团队协作或建设业务数据体系时使用。  
> **开始前：**确认业务边界及负责人员。  
> **完成后：**发布主题域版本，模型、标准和业务注释等可按支持的关系引用。  
> **当前要求：**主题域关联为可选；已选择关联时，必须采用可用的已发布版本。各治理定义的责任人、维护人仍须填写。

术语示例：“有效客户”应写清判定条件、时间范围和业务边界；真正筛选有效客户还需要在数据流配置对应条件，不能让用户误以为填写术语就执行了筛选。

专业名称保留，在附近提供白话说明和当前对象示例。区分“责任人”与“审批权限”、“数据流”与“工作流”、“字段约定版本”与“成果发布状态”。

## 6. 进入平台前的虚线框学习引导

### 6.1 建议形态：分章节学习，再进入正式操作

按本次诉求，默认首次进入先展示欢迎 Dialog，说明“先了解业务关系和基本操作，再进入正式平台”。点击“开始学习”，进入与正式平台布局一致、明确标注“教学示例”的学习模式。完成基础学习后，点击“完成学习，进入平台”进入真实工作台。

学习可暂停并保存进度，之后继续；已完成的用户正常进入，学习中心随时重看。基础学习与各模块的深入教学分开记录，不要求用户一次连续学习所有字段。首次模块深入教学在模块入口提示，正式业务中的短说明始终保留。

### 6.2 虚线高亮和说明的关系

- 每次只用虚线框高亮一个目标区域，配合序号和文字；其他区域降低视觉强调。
- 提示清楚说出“这是什么、为什么要做、前一步是什么、做完到哪里”，不只写“点击这里”。
- 教学在单层大尺寸 Dialog 内展示示例界面与当前说明，目标高亮定位示例中的菜单、表单或底栏；正文可内部滚动，避免额外悬浮第二个操作弹窗。
- 暂停、上一步、下一步、完成并进入平台都在该 Dialog 右下角，固定位置。虚线框旁不再另放一套操作按钮。
- 教学模式仅使用明确标记的示例对象；示例点击只演示状态变化，不读取真实业务行，不创建生产模型、执行真实任务或办理发布、授权、清理。
- 若示例数据展示“已完成”“已授权”，须始终处于教学标签内，不能带入正式工作台当作真实状态。
- 按账号、角色及教学内容版本记录学习进度；学习完成不赋予角色、审批权或资源访问权。没有某职责的用户仍能理解协作关系，但不会获得对应真实操作入口。
- 不依赖虚线颜色单独传递信息；步骤名称和序号可读，键盘可前后切换，窄屏不遮挡目标或底栏。
- 教学结束恢复正式模式；正式办理仍执行完整业务前置、版本、质量和审批要求。

### 6.3 基础学习的八个主题

每个主题先讲关系，再高亮少量核心区域；复杂操作另有模块章节，不把所有功能拉成一条几十步导览。

| 顺序 | 学习主题 | 虚线框重点 | 用户应学会什么 |
|---|---|---|---|
| 1 | 认识平台分工 | 工作台的业务关系图、平台入口 | 共享交换准备来源和办理共享，治理负责认识/加工/核验，资产承接成果发布与发现 |
| 2 | 为什么需要业务规范 | 主题域与责任、数据标准、业务术语入口 | 分类、责任、业务含义和数据规则各解决什么问题；哪些当前必需、哪些按场景使用 |
| 3 | 认识数据与读取条件 | 元数据来源名称、结构、加工权限提示 | 同名来源可能不同；可见不等于可读取，来源结构和字段权限影响后续治理 |
| 4 | 约定结果 | 模型字段、主键、敏感范围、输出要求 | 模型说明想得到什么；模型发布和实际生成数据是不同环节 |
| 5 | 处理与质量检查 | 数据流画布、选中节点配置、质量分支、右下底栏 | 数据怎样经过处理；每个算子为什么用；发布定义后仍需真实运行 |
| 6 | 编排、调度与实际运行 | 工作流依赖、独立调度菜单、运行状态入口 | 如何组织任务、何时自动执行、在哪里判断真实成功或失败 |
| 7 | 成果发布与共享 | 质量/完整性状态、成果发布、共享后续入口 | 哪些条件阻断发布；普通发布与工作流审批区别；成果发布不等于公开或获得使用授权 |
| 8 | 持续治理 | 问题整改、血缘影响、告警、保留清理及迁移入口 | 发生异常、变更或结果过期之后应走哪条完整处理流程 |

### 6.4 模块深入教学示例：数据流开发

1. 高亮来源：说明读取哪份数据、哪些字段，先检查契约和加工权限。
2. 高亮画布：说明节点连接表示实际处理顺序，选择算子取决于业务需要。
3. 高亮当前节点属性：填写一个节点的配置，避免在长页面寻找全部配置。
4. 高亮质量与输出：解释业务检查、合格分支、模型字段及敏感范围要求。
5. 高亮版本和右下操作栏：依次解释保存草稿、发布定义、发起运行和查看结果；教学中的按钮只演示。
6. 高亮实际结果位置：说明合格/隔离计数和成果入口，指出后续门禁与发布办理位置。

退出学习后回到真实数据流列表，示例配置不自动保存为正式定义。

这些是基于官方公开文档确认的模式，尚未对外部付费产品进行登录实测。下列内容为适配 DataMesh 的设计判断，不声称参考产品的全部功能已存在于本平台。

### 8.2 本平台的九项交互约定

1. **以当前对象为中心。**来源、模型、数据流、成果详情顶部始终说明对象名称、用途、负责人、适用版本和状态。技术编号保留用于核对，不让编号代替业务名称。字段、质量、运行、血缘和相关对象按标签或关联入口查看。
2. **条件与下一步相连。**例如“输出模型尚未发布”旁提供进入该模型核对的入口；“等待其他职责办理”说明需要谁处理。前置条件采用“待核验、已满足、不满足、待他人办理、不适用”，没有证据时不标成已通过。操作禁用时就地说明原因，不只放一个灰按钮。
3. **专业名词可就地理解。**名称保留，附短解释；点击或键盘触发后可看当前对象示例及它被哪些内容引用。解释内容在当前 Dialog 内展开，不开启第二层操作弹窗。责任分工、术语、标准、模型分别说明其作用，不混成一个“规则”。
4. **图形与配置联动。**数据流中部显示处理图，选中一个节点后只展示该节点的属性；字段结构、处理关系与输出要求联动说明。工作流图展示任务依赖及条件，选中任务后核对输入和前置。所有现有算子和任务类型继续可用，不以模板替代完整能力。
5. **设计状态与真实执行分开。**配置视图说明准备怎样处理；运行视图说明某次执行实际发生什么，标明定义版本、参数、时间、处理及隔离计数。切换版本后不能把旧运行统计当成新配置结果。没有执行记录时显示尚未运行，不给绿色成功标志。
6. **质量异常能逐层解释。**先给用户可理解的结论，再提供未通过规则、涉及字段、实际范围和处理入口，最后按需展开诊断码及追踪信息。只有现有权限允许时才显示真实记录；敏感值仍遵循现有隐藏或脱敏规则，教学示例不冒充正式异常数据。
7. **血缘图可以帮助做判断。**点选对象查看真实上游、下游和字段关系；按需要展开局部，避免首次显示一张难理解的大图。说明每条关系的含义和版本，受限或不完整范围明确提示。只基于已有证据展示关系，不由用户拖线虚构真实血缘。
8. **反馈形成闭环。**保存后说明保存了什么以及下一步；提交运行后能看到排队、执行和结果；失败后能定位原因和回到适合的配置。空列表说明为什么为空、需要准备什么、从哪里开始；加载、权限不足、无记录、确实失败分别表达。
9. **按既有职责提供默认工作重点。**业务理解偏重用途、口径与成果；治理人员偏重结构、模型与处理；负责人偏重待办、核对与影响。入口排序及提示可适配既有角色，同一对象、业务规则和权限依据保持一致，不设置一套规则较少的业务模式。

### 8.3 代表性页面的具体使用方式

| 页面或Dialog | 首先让用户理解什么 | 内容组织 | 关键交互与后续衔接 |
|---|---|---|---|
| 治理工作台 | 当前有哪些工作、处在哪个环节、需要谁继续 | 我的事项、业务关系、近期对象和学习入口；统计按需查看 | 点事项带入真实对象；点关系环节解释用途、前置和后续，不强迫照一条长向导逐项点击 |
| 主题域与责任 | 范围如何划定、为什么要明确责任 | 业务范围、人员分工、关联定义分标签或区域 | 选择已有主题域可看到范围及引用；解释责任与账号权限区别；变更时查看已有引用 |
| 数据标准与业务术语 | 规则和业务含义各解决什么问题 | 定义、适用示例、实际引用、版本 | 点击关联字段或对象在当前Dialog切换内容并可返回；明确“已发布”与“已被引用使用”是不同事实 |
| 元数据与数据剖析 | 来源是什么、字段是什么意思、观察覆盖多少数据 | 结构、业务注释、输入要求分区；剖析为独立入口 | 从某来源进入剖析自动带入对象；报告明确采样/全量、时刻和敏感范围，不能误认为修改了来源 |
| 数据建模 | 最终结果应该长什么样 | 字段及约束、实体关系、版本、物理模型建表分标签 | 字段与标准关联就地解释；输出要求可核对；建表预览、执行回执和数据处理结果明确区分 |
| 数据流开发 | 每个节点为什么存在、前后连接意味着什么 | 对象列表管理；设计Dialog采用处理图、当前节点属性和可切换的结构/校验信息 | 点选节点时展示输入字段和输出字段的结构关系；保存/发布/运行在右下；看结果时明确本次真实版本和计数 |
| 工作流编排 | 哪个任务需要先完成、成功失败后如何继续 | 任务依赖图、当前任务属性、版本与运行信息分区 | 点选任务查看前置和输入；有待审批任务时解释等待哪个职责，完成后去哪里查看 |
| 调度计划 | 什么时候执行、按哪个时区、错过后怎么办 | 时间规则、参数、启停状态、触发记录分标签 | 用可读日期展示未来触发时间；规则改变后重新核对；从触发记录进入对应真实运行 |
| 质量检查与整改 | 哪条要求不满足、如何证明处理完成 | 结论、规则/字段/范围、运行证据、整改记录分层 | 点规则看适用条件和结论；从异常带入原运行登记问题；整改后由真实复测核验闭环 |
| 血缘与影响 | 数据来自哪里、改动会影响谁 | 局部关系图与可切换的依赖表、字段关系 | 点选对象解释关系并进入详情；保留原分析范围和返回位置；展示可见范围限制 |
| 成果发布与生命周期 | 现在是什么成果、是否满足发布条件、下游是否在用 | 成果概览、发布核对、依赖和生命周期办理各有明确入口 | 来源/模型/运行/质量互相可达；下架、清理、迁移分别说明后果和前置，不把它们压进一张长表单 |

“可视化”优先展示字段结构、对象关系和真实状态。是否增加处理前后的真实数据预览，需要核对现有读取能力和访问策略后单独评估；本方案不把预览真实记录列为使用引导的必要条件。

### 8.4 一个具体示例：用户发现客户成果不能发布

以下为交互示例，不是当前主环境故障结论。

1. 用户从成果列表打开“客户基础数据”，先看到它的来源、模型版本、生成时间和当前发布条件。
2. 页面显示实际返回的阻断原因。若为来源结构变化，则解释“此成果依赖的来源结构与当前契约不一致，需要核对来源及引用”。不使用泛化的“发布失败”代替具体原因，也不猜测未返回的变化字段。
3. 用户在右下角选择“核对来源”，当前Dialog切换到对应来源信息，保留成果和返回入口。
4. 根据真实变化及权限，到相应功能办理资源契约和处理定义修订；必要时查看下游影响和迁移安排。
5. 新版本实际运行后产生新成果，用户查看新的质量与完整性结论，再按原规则核验发布。

这个过程保留全部业务工作；交互改进在于对象已带入、原因可理解、处理入口明确、用户知道应回到哪里继续。跨不同成果或版本时明确说明已切换对象，旧成果的证据不会被新结果覆盖。

### 8.5 首轮采用与后续独立评估

首轮采用：对象概览、短解释、前后关系提示、带上下文跳转、单层Dialog切换、分区设计、真实运行反馈、可解释的异常、虚线高亮教学及专业菜单拆分。

需要新增接口的关系汇总或跨对象查询，应基于真实可见对象提供，不能在前端猜测。统一跨类型搜索、自由SQL探索、自动认证、智能质量评分、AI自动生成规则、术语自动授权和复杂数据产品体系均不是当前已确认的功能范围，不因参考其他产品而顺带加入。已有名称搜索和筛选继续可用。

这些交互有望降低理解和寻找入口的成本，实际效果以未参与建设的业务用户完成代表性工作时的表现验证；不将参考成熟平台等同于已经证明本平台体验更好。

## 9. 方案落地顺序与验收

1. 按已确认的菜单职责、功能关系和必选口径，结合本次交互约定，形成全部页面统一的说明内容与代表性页面交互稿。
2. 按菜单拆分工作流/调度、标准/术语、元数据/剖析及生命周期中的独立工作；保留对象上下文和原有能力。
3. 改治理工作台，展示真实进度、待办、业务关系和准确的继续入口，收起大段默认展开的说明。
4. 建设基础教学、虚线高亮和模块深入教学；用明确的教学示例与正式业务状态隔离。
5. 完成来源、模型、数据流、运行、质量、发布及共享后续之间的带上下文衔接；每个业务环节仍在职责明确的功能中办理。
6. 按已确认方式实现后验证、用真实已有来源核对完整流程，并备份部署主环境。本轮只提交方案，不启动实现或部署。

验收标准：

- 从未参与建设的人员能说清主题域、责任、术语、标准、模型、数据流、工作流和调度的用途及区别。
- 能指出当前工作必须满足哪些前置、可复用哪些已有对象、当前状态是否真实完成、下一步由谁在哪里办理。
- 全部现有功能、算子、版本、门禁、审批、异常及迁移流程有明确归属，没有以简化为由删除或绕过。
- 不要求复制编号串联常用路径；适用的对象引用自动带入，仍允许核对版本和范围。
- 教学学习完成与业务办理完成明确分开，教学期间无生产写入；已完成用户不反复被整段教程打断。
- 所有业务 Dialog 单层、内部滚动、底栏右下角，桌面和窄屏均可操作；非数据专业用户能通过就地白话解释完成工作。
