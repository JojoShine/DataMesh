# 数据治理操作指南

## 公开体验账号：先操作体验空间

公开测试账号进入治理后，自动打开当前浏览器独立的“治理体验空间”。页面带有“治理体验 · 当前浏览器生效”标记，保存的配置、导入文件和处理结果不上传正式业务库，也不与其他访问者共享。

1. 在“数据流设计”选择“居民信息整理与质量检查”，点击“运行”。内置80条虚构居民记录，清理姓名空白后输出78条，隔离姓名缺失和年龄异常的2条。可以查看输入字段、处理步骤、实际计数和结果模型草稿。
2. 在“轻量治理”选择“居民信息轻量处理”，修改步骤后点击“保存并运行”，查看处理结果与隔离记录，并用“下载体验 CSV”导出本浏览器的结果。
3. 在“数据建模”“数据标准”“业务术语”“检查方案”中新建或修订配置，保存独立版本。体验空间内的发布仅影响本地定义，不代表正式审核或服务器发布。
4. 居民信息与报名登记都含有`person_id`，可在数据流中添加关联表，配置对应字段后运行；也可继续筛选、去重、分组汇总，或使用普通数据流任务组成工作流。
5. 看板与质量趋势来自本浏览器实际进行的体验操作；重新打开页面可继续查看。需要重新开始时，点击“重置体验空间”并确认，只清除当前浏览器的体验数据。

体验CSV使用UTF-8（可带BOM）、逗号分隔，首行为字段名。每份最多1 MiB、50列、1000行；每个处理单元最多8份文件，每次处理最多1000行、30个节点，工作流最多10个普通数据流任务。保留最多30次运行，本地记录总大小不超过3 MiB。整数求和保留精确结果，超出安全整数范围或需要精确小数计算时会明确拒绝。

主数据匹配确认、指标专用计算、持续监测和自动保留清理需要正式环境；体验空间可以维护相关配置，样本统计可在数据流中使用分组汇总。自定义Python/JavaScript、自定义正则标准、外部连接和回调、持续运行与后台定时调度、物理部署及正式发布审核需要正式环境。体验空间不会把这些操作伪装成已完成，也不会生成正式服务端核验证据。以下章节说明正式账号的完整业务流程。


数据治理把已有数据整理成可核验、可追溯、可共享的成果。CSV 文件可从“轻量治理”直接开始，无需治理空间；使用已登记来源时先选择治理空间，再确认来源与加工权限。单表处理可以直接使用数据流，多个任务需要配合时再使用工作流。

## 按业务流程找到入口

| 顶部菜单 | 办理内容 |
| --- | --- |
| 工作台 | 查看治理进度、运行情况与待处理事项 |
| 准备数据 | 选择来源、认识字段，按需约定结果模型 |
| 处理数据 | 上传 CSV 轻量治理，或配置数据流、工作流与定时运行 |
| 检查与交付 | 查看质量记录、整改复查、核验成果及管理生命周期 |
| 标准与规范 | 维护主题域、责任、业务术语与数据标准 |
| 监控与追溯 | 查看运行、处理告警、追查来源与变更影响 |

常用顺序是“准备数据 → 处理数据 → 检查与交付”。质量检查可在处理前、处理中或处理后使用；规范维护、故障恢复和成果追溯可按需直接进入。数据流可以独立运行，无需先创建模型、工作流或调度计划。来源接入及加工授权在共享交换办理，成果发布保留既有核验与审批流程；完成共享交换的目录挂载、审核及启用后，使用者可从数据资产的“资产发现”申请，在“我的资产”使用。

## 看板指标怎么看

治理看板按“准备数据、处理数据、检查与交付、标准与规范、监控与追溯”组织指标，点击名称进入当前业务入口。

- 来源、模型、数据流、工作流和检查方案按对象计数，不重复累计历史版本；批处理和持续更新按数据流最新版本区分。
- 运行次数、成功率和质量趋势采用所选周期；质量按检查节点计行次，同一行经过多个节点会分别计次。质量管理的检查次数按实际产生检查的运行去重，不代表检查方案数或通过成果数。
- 持续任务展示当前登记状态，运行中不等于数据已追平；定时计划单独按数据流、工作流目标统计。
- 轻量治理仅展示自己的处理单元、文件和期间运行，跨空间保留；不计入空间成功率、质量趋势或正式成果发布，管理员也不能汇总其他人的私人轻量治理。
- 可见来源不代表已有加工授权；已发布成果也不代表当前可交付，进入对应页面核对实际条件。

## CSV 文件直接整理

在“处理数据 → [轻量治理](/platform/governance/lightweight)”上传 CSV，即可关联、清洗、检查并下载结果，不需要登记目录、选择空间、建立模型或发布定义。账号仍需数据治理平台和治理角色权限。

1. 输入处理单元名称，上传 UTF-8（支持 BOM）、逗号分隔、首行为字段名的 CSV。每个单元使用 1–8 份文件，每份最多 20 MiB、100 列、100,000 行；空或重复表头、列数不一致等错误会明确提示。
2. “选数据”选择主表并勾选需要的字段。文件全部按文本读取，保留编号前导零；原始中文等表头作为显示名称保留。
3. 按需添加关联表，在“定规则”选择两边的对应字段及匹配方式。可依次添加字段保留、去空白、大小写统一、筛选、去重和必填、唯一、长度、枚举或跨字段比较等质量要求。
需要自定义校验时，从“添加整理步骤”选择“自定义脚本检查（Python / JavaScript）”。选择语言和可用运行环境，编写 `transform(row, context)`，每条记录返回一个对象，并声明完整输出字段。可参考编辑器中的质量检查示例，返回 `quality_status` 文本字段，再添加质量检查，设置允许值“通过”，将不合格记录隔离。脚本异常会停止运行，查看错误提示和代码行号后修改；运行环境与方案版本固定。脚本可显式转换类型，数值输出可继续设置数值范围检查。

4. “确认输出”核对最终字段，点击“保存并运行”。运行固定本次文件和方案版本，结果保存在私有运行记录中；可查看每个节点的真实配置、结果行和隔离原因，下载完整 CSV。
5. 保存的处理单元仅本人可见，可重新打开并调整。选择历史运行时显示该次固定版本；修改后点击“保存并重新运行”创建新的执行记录。排队或运行中可取消；失败记录保留，修正后可重跑。

例如：上传一份订单明细和一份地区资料，按地区编号关联，清理客户名称首尾空格，检查订单编号必填且唯一，再下载合格结果。轻量治理不会自动把文件或结果注册到共享目录。

## 使用已登记来源之前

1. 确认账号已开通数据治理平台，并具备治理角色及相应资源职责。
2. 在“空间管理”新建或选择业务空间。空间用来组织来源、模型、数据流、运行和成果，不会自动授予来源权限。
3. 在“来源数据”中添加可用资源，核对原提供部门、资源状态、可用字段和加工范围。
4. 到“元数据管理”认识字段含义、类型与范围，必要时运行数据剖析，先了解缺失、重复等情况。

来源未就绪或加工权限不足时，先在共享交换办理，不要通过重复建空间或模型绕过前置条件。进入业务页面后，先确认顶部显示的是本次工作对应的治理空间。

## 从接入到使用的完整流程

1. **接入与授权**：共享交换登记来源、目录和资源，治理人员取得来源及字段加工权限。
2. **治理与产出**：在治理空间中确认来源、设置处理规则与输出，完整运行数据流；多个任务按需通过工作流组织。
3. **核验与共享**：检查成果质量、完整性和有效期，办理成果发布，再到共享交换关联目录、挂载和审核。
4. **申请与使用**：使用方找到已发布资源，选择原始或治理后版本，按用途申请，获批后在授权范围内使用。

保存方案、发布定义、运行成功和成果发布是不同状态。样本试运行用于检查逻辑，不代表已经生成完整、可发布的成果。

## 选择处理方式与数据分层

每个数据流版本固定一种处理方式：批量或流式。保存的是处理定义，执行后产生独立运行记录。修订会生成新版本，已有版本和成果保留。批流方式决定如何处理数据，调度决定何时启动一次批量执行。

- **批量处理**：用于一次清洗、定时整理、跨表核对和周期汇总。读取授权来源的本次数据，在 Doris 完成 SQL 处理，结果也保存到 Doris。Python / JavaScript 步骤仍由隔离执行器运行。流程不会因数据量变化暗中改用另一个引擎；超过运行限制会明确阻断。
- **流式处理**：用于来源新增、修改、删除后需要及时反映的结果。先在共享交换启用 CDC，完成首次采集，再在已发布数据流的“持续运行”页启动。来源经 Kafka 进入 Flink；Flink 的已提交事务结果由平台写入 Doris。页面分别显示来源采集、Flink 计算和 Doris 进度标记的可读状态，以及来源事件时间、已转入计算的时间与待转入位点数。健康检查时间只说明何时检查，不代表数据已同步到该时间；待转入位点数不包含尚未采集的来源变化，也不能代表 Flink 全链路积压。无法追溯的已处理源事件时间和端到端延迟显示“未知”。
- **暂停与恢复**：暂停会保存 Flink 恢复点，等待已提交结果进入 Doris。暂停成功后可生成固定成果，再按通常流程确认模型、核验、发布。恢复沿用原恢复点。暂停仍保留任务名额；不再需要更新时选择“停止持续运行”，平台确认作业停止后释放名额。结束后保留已生成成果，若需重新处理则启动新任务。运行中查看的是最新处理结果，不能替代成果发布核验。
- **RustFS 存档**：在成功运行的结果详情点击“保存至 RustFS”，生成带校验和的固定文件快照。存档不会随 Doris 后续更新而自行变化，需要时重新生成；它不反向覆盖最新成果。

持续更新首次启动要求 CDC 首次快照完整、日志未缺失且当前来源为单分区。当前支持投影、清洗、筛选、去重、关联、聚合、Python／JavaScript代码步骤和受支持的质量检查；尚未接入持续处理的质量规则仍会在启动前提示。代码按单行在隔离环境执行，不保留解释器全局变量作为跨行状态；已计算的同一行输入会复用持久结果，以保证更新撤回、暂停恢复和重放的一致性，跨行状态请使用关联、聚合等步骤。数值精度最高38位，时间精度最高微秒。来源权限或结构失效时停止转入数据并核对作业状态，不跳过缺失日志继续处理。

- **原始接入 · ODS**：Doris 来源区，保留本次授权读取的输入，不直接当作已治理成果发布。
- **标准明细 · DWD**：标准化、清洗后的明细，普通治理输出默认选择。
- **公共维度 · DIM**：可复用的区域、机构、分类等维度数据。
- **主题汇总 · DWS**：按主题统一口径的汇总数据。
- **应用服务 · ADS**：面向具体报表、应用或共享场景的结果。

在“数据建模”选择业务用途：整理统一的业务明细对应 DWD，维护可复用的基础资料对应 DIM，汇总可复用的统计指标对应 DWS，提供特定报表或应用所需数据对应 ADS。原始数据在接入时归入 ODS。概念模型可以暂不确定用途，逻辑和物理模型在保存时确认用途。数据流绑定模型后自动继承所选版本，不再重复选择；根据结果生成模型时，在“确认输出”选择成果用途，生成的模型沿用该用途。历史未标注的模型沿用数据流原分层，没有设置时按 DWD 兼容处理，页面会明确提示。模型用途修订不会搬迁已有成果，需要绑定新版本并重新运行。模型列表的分层选项仅用于筛选。元数据、成果核验和血缘中也显示该信息。分层与“概念 / 逻辑 / 物理模型”不同，也不会改变原提供部门、业务目录和权限。质量异常与临时计算放在独立内部区域，不混入以上业务层。

## 常用工作流怎么处理

### 单表清洗与质量检查

适合统一姓名格式、删除重复记录、筛选业务范围或检查必填和唯一等要求。

1. 打开[数据流设计](/platform/governance/dataflows)，新建或选择数据流。
2. 按“选数据、定规则、确认输出”依次填写：选择来源与字段，按需增加去空白、去重、筛选和质量检查，最后确认输出字段或结果模型。
3. 单一路径会自动衔接前后关系；多表可在“选数据”添加关联表，多分支或代码处理使用高级编排。
4. 点击“保存并运行”；已保存草稿可用“检查并运行”。按检查提示补齐配置，并以真实完整运行结果为准。
5. 到“成果核验”查看质量与完整性。若本次选择根据结果生成模型，按下节完成模型确认、发布、绑定及重新运行。
6. 质量问题进入“质量整改”处理；修改后重新运行或复测，不能只关闭问题记录就认为成果已修复。

例如：对业务明细中的名称去首尾空白，检查记录编号非空且唯一。去空白只整理已有文字，不会补全原本缺失的名称。

### 多来源关联与汇总

适合把业务明细、主体基础资料、分类字典等多份数据按业务键关联，或按区域、类别汇总结果。

1. 确认各来源均已加入当前空间，读取与加工授权有效，关联键含义、类型和数据范围一致。
2. 在数据流的“业务步骤”中先选择主表，再在“选数据”区域点击“添加关联表”，逐张选择需要补充的数据和字段。每添加一张表，点击横向步进栏的“定规则”，再选择相应的“关联数据表”步骤，选择“已有数据的对应字段”和“关联表的对应字段”，再选择保留原有全部记录或只保留匹配记录。系统会自动衔接后续处理，无须手动连线。
3. 明确输出字段和结果模型，检查重名字段、不匹配记录以及重复匹配对结果条数的影响。需要第三张及更多表时，继续点击“添加关联表”；移除关联表时，对应关联步骤一并移除，请重新核对后续字段。多分支、关联表先单独清洗等复杂关系仍在高级编排中维护。
4. 完整运行后核对关联结果、隔离记录、处理条数和质量报告。
5. 不符合预期时回到数据流调整；来源不全或样本成功都不能代替完整成果核验。

### 定时执行与异常处理

适合定期更新同一批业务数据，或安排“先加工、再检查、最后人工审批”的任务链。

1. 先保存并发布所需数据流版本，手动完整运行确认可用。
2. 需要多个任务配合时，到[工作流编排](/platform/governance/workflows)添加任务，选择已发布数据流版本，明确任务之间的先后依赖；单个数据流不必额外创建工作流。
3. 按需添加独立质量门禁或成果发布审批。普通成果发布与工作流中的人工审批分别办理。
4. 保存并发布工作流版本，再手动运行核对任务状态和成果传递。
5. 单个批量数据流可直接在“定时运行”中设置周期、时区、首次触发时间和参数；多任务则调度工作流。所有计划都可以在[调度计划](/platform/governance/schedules)统一查看、暂停、启用和核对触发记录，无需重复配置。流式处理直接启动长驻运行，不使用周期调度。
6. 到“运行运维”查看每次执行。失败时按诊断处理，质量异常进入质量整改，修复后再重试或复测。

调度固定使用所选版本。发布新版本后，在原计划的“管理调度”中选择“调整计划”，核对目标已发布版本、参数与时间规则，确认未来五次触发时间后保存。计划编号、暂停/启用状态和触发历史保留；不会创建第二份计划，也不会自动切换到最新版本。并发修改会被阻止，请刷新后重新核对。

常用周期可直接选择每小时、每天、工作日或每周；固定间隔可选择数值与时间单位，高级日历规则按需填写。首次触发按所选时区解释。夏令时不存在或重复的首次时刻需重新选择；日历规则的后续触发遵循页面提示的夏令时规则。

## 根据结果生成真实模型

输出结构尚未确定时，可以在数据流中选择根据结果生成模型。工作流执行这类数据流时，也使用同样的模型生成流程。

1. 完整运行后，系统会保存本次推断得到的真实模型草稿。
2. 在运行结果中点击“查看已生成模型”，或到[数据建模](/platform/governance/models)查看当前空间中的草稿，核对字段、类型、名称及责任人。
3. 确认并发布模型，在模型页选择“返回数据流并绑定此版本”。核对来源运行和当前数据流版本，再生成待复核修改；确认后保存为新版本并完整运行。已有未保存修改时，先保存或明确放弃，避免丢失。
4. 重新运行后，核对成果是否符合模型约定，再办理成果发布。

生成模型草稿不等于模型已发布，也不等于本次推断结果已是可共享数据集。历史推断结果可通过“根据结果生成模型”补建草稿；先确认当前空间和对应运行，避免找错模型。

## 核验成果并关联目录

入口：[成果核验](/platform/governance/results)。

1. 打开本次完整运行产出的成果，核对来源、处理内容、质量结果、完整性和结果有效期。
2. 处理阻断项后，由具备相应成果发布职责的人员办理发布。工作流包含发布审批任务时，还要按该任务的审批要求办理。
3. 单表治理成果归属于原提供部门，并显示原来源、原目录及本次治理了哪些内容。
4. 需要共享时，默认选择“关联回原目录”；确有独立业务分类需要时，可选择“新建目录”。
5. 进入共享交换完成字段映射、挂载校验、审核及启用。使用方随后可以分别选择原始资源或治理后资源申请。

成果的“共享办理”页会读取可见目录与挂载的真实状态；有草稿修订时需区分修订与当前启用版本。无法读取的证据显示待核对，不能据此认为没有挂载。使用申请和授权按具体使用方核对，挂载启用不代表所有人都能使用。

原始资源和原目录会保留。成果发布不会自动替代目录审核，也不会自动授予使用方数据访问权限。多来源成果没有唯一原目录时，应根据成果用途选择关联目录。

## 各功能的用途与衔接

以下保留各功能的业务解释和实际例子。按当前任务查阅，不要求逐项创建。

### 从接入到共享

**业务用途**：把分散、口径不一的来源整理成有明确含义、质量依据和责任归属的数据成果，供后续业务使用。

**适用场景**：需要统一客户或商品数据、形成可复用数据集，或持续跟踪已有成果是否可信时。

**必选与可选**：可读取来源、加工权限、结果模型、完整运行和发布核验是这条业务链的必要条件。主题域、标准、术语按业务需要关联；工作流用于组织多个任务，定时执行可直接调度批量数据流或工作流。

**前置条件**：共享交换提供来源、资源契约和加工授权；业务人员明确用途与口径，治理人员据此约定结果和处理逻辑。

**后续衔接**：元数据说明来源，模型约定结果，数据流实际处理，质量检查提供证据。成果发布后，共享交换继续办理目录挂接、审核和使用授权。

**实际例子**：客户服务部要提供“客户基础信息”：先确认客户表与加工权限，再建立客户结果模型，配置姓名去空白和编号非空唯一检查，完整运行后核验发布。商品运营部整理“商品基础信息”也走同一流程，可复用已有规范，按需再配置每日调度。

### 主题域与责任

**业务用途**：按客户、商品等业务划分统一边界，而不是按系统各建一套同名主题域。企业定义回答这是什么业务，部门分工回答本部门负责哪部分、由谁确认和维护。

**适用场景**：CRM、商城、售后都保存客户信息，需要统一客户范围，同时由不同部门分别维护资料、交易与服务数据时。

**必选与可选**：企业统一定义由管理员建立和发布；各部门可按需登记独立的责任分工，也可继续使用原有部门主题域。责任人和维护人始终必须是记录所属部门的有效治理人员。

**前置条件**：企业先明确业务包含和不包含的内容；部门责任引用已发布的企业版本，并补充本部门职责。草稿、部门分工和业务资源仍按现有权限控制。

**后续衔接**：标准、术语、模型和业务注释可关联企业主题域或本部门分工。归入同一主题域不代表客户编号相同，不会自动去重、合并来源或开放跨部门数据。新版本需评估后明确迁移。

**实际例子**：管理员发布“客户 v1”，定义企业客户的业务范围。销售部登记“客户·销售责任”，说明负责客户联系资料；售后部登记“客户·服务责任”，说明负责服务记录，各自指定本部门人员并发布。两份分工引用同一企业定义，但各部门看不到对方的受控分工和来源数据。商品域同理可由商品运营部负责商品信息、财务部负责核算口径。

### 数据标准

**业务用途**：把可复用的业务含义落实为类型、格式和允许值约束。一份标准可以被多张表的字段引用，无须按表重复建立。

**适用场景**：不同系统的启停标志、客户编号、金额精度等需要一致表达时；同名字段应先核对业务含义，不能只因都叫status就合并。

**必选与可选**：标准编码是业务标识，不绑定表名。码表中的每个允许值都要说明业务含义；旧版本缺少含义时仍能读取和引用，补充须建立新版本，不覆盖历史。

**前置条件**：先确定表达的业务概念、类型和约束是否相同；按需关联已发布企业主题域或本部门责任。标准仍按所属部门权限维护，主题域共享不代表标准跨部门共享。码值含义不能仅由0、1推断。

**后续衔接**：模型字段和元数据注释按固定版本复用标准。数据流负责把来源编码转换为标准值，输出校验确认符合约束；标准发布本身不会清洗数据，也不会自动改写旧引用。

**实际例子**：建立“启停标志”标准，编码common.enable_flag，整数类型，码表0＝停用、1＝启用。客户表enabled与商品表is_enabled含义和约束一致时，共用该标准。订单pay_status中的0＝未付款、1＝已付款，含义不同，应另建付款状态标准。编码中的common是业务命名范围，不是数据库表名。

### 业务术语

**业务用途**：明确“客户”“活跃”“有效”等业务概念的含义和适用范围，让采用同一口径的人理解一致；同名但业务含义不同的概念应明确区分。

**适用场景**：同一个字段或指标在不同部门有不同理解，或需要向非数据专业人员解释口径时。

**必选与可选**：按需建立或复用术语；引用时需使用已发布版本。术语解释业务含义，不直接限定技术类型或执行数据筛选。

**前置条件**：业务上先确认概念适用的对象、时间范围、判断条件及例外；责任人负责确认口径，维护人负责持续维护。

**后续衔接**：元数据业务注释可以把技术字段与术语连接起来；标准进一步约定字段表达，数据流实现相应处理。术语变化时需要核对下游注释和处理方案。

**实际例子**：“活跃客户”可定义为“统计日之前30天内至少有一笔已支付且未全额退款订单的客户”。在术语中写清统计时点和业务边界，发布后关联客户字段的业务注释。需要实际筛选时，还要在数据流中实现对应条件；术语本身不筛选数据。

### 模型、输出契约与建表

**业务用途**：在处理前约定最终要交付的数据长什么样、应满足什么要求，让来源、处理人员和使用方对成果有共同预期。

**适用场景**：需要形成统一客户表、商品表，约定成果字段和可用时限，或将结构落实到目标数据库时。

**必选与可选**：正式成果发布前需按已发布模型核验；探索处理可先运行，再根据结果生成模型。标准和实体关系按需关联；只有需要创建真实目标表时才使用物理模型建表。

**前置条件**：先确认来源字段及业务含义；引用的标准、关联模型须是已发布版本。模型需要与实际处理后的字段匹配。

**后续衔接**：元数据描述已有来源，模型约定希望得到的结果；数据流负责实现转换并接受模型约束。成功成果再经过质量、完整性、结果有效期及发布职责核验。

**实际例子**：商品模型可约定 product_id 为非空主键、product_name 为文本、price 为精确小数(18,2)。价格不得小于0另配到数据流质量检查；允许不合格比例设为0，表示有不合格记录时阻止成功产出。结果有效期设为86400秒，表示超过一天需重新运行。

### 认识字段、说明含义和跟踪变化

**业务用途**：共享交换负责接入资源，元数据从源库自动获取技术结构；业务人员解释字段含义并确认归属，帮助使用方理解数据及其变化。

**适用场景**：开始治理一个来源、接到陌生字段，或来源变更后需要判断下游是否还能继续使用时。

**必选与可选**：已接入资源在存在有效治理授权时自动建立每日采集计划，可调整周期或暂停。库表读取真实结构，文件/API保存登记契约，不能视为已验证实际内容。业务说明与数据情况检查按需补充。

**前置条件**：先在共享交换登记表、文件或API资源，再在当前治理空间的来源数据中完成关联。元数据只查看这些来源，读取内容仍需对应加工授权；治理成果不直接作为新增来源。来源关联与“版本一致”仅说明管理范围和结构状态，不能当作已获得加工授权。普通人员的加工授权由来源责任部门在共享交换办理；管理员按现有平台权限直接治理，不会自动生成数据使用申请记录。

**后续衔接**：采集无变化时复用快照，失败保留旧结构并提示，不能把连接失败当成源表删除。结构变化形成待办，结合影响分析记录处理安排；新观察不覆盖人工注释、不自动修改交换契约、模型或运行任务。

**实际例子**：CRM客户表接入后自动采集 customer_id、name、amount。业务人员把 name 解释为“客户姓名”，说明客户编号与会员编号的区别。源库新增 customer_level 时，采集生成变化待办；销售部解释等级含义，核查模型、数据流及目录影响，再分别更新契约和引用。商品表新增保质期字段时同理。

### CSV / XLSX 输入

**业务用途**：为表格文件明确每一列的名称、类型和约束，使文件能够像数据库表一样参加数据治理。

**适用场景**：商品价目表、客户清单等以 CSV 或 XLSX 交付，需要进行统计、清洗或质量检查时。

**必选与可选**：结构化读取 CSV/XLSX 前必须有有效输入契约；普通 PDF 等文档仍按完整文件管理，不作为结构化行处理。

**前置条件**：文件已在共享交换接入，维护权限有效，并有与表头同名、类型匹配的已发布模型；支持 UTF-8 CSV 或 XLSX，上限20MiB、10000行。

**后续衔接**：模型提供列约定，文件核验将约定固定到新契约版本；下游挂接、授权和数据流需与对应版本一致，才可读取结构化行。

**实际例子**：商品价格CSV包含 product_id、product_name、price 三列。商品模型约定它们的名称、类型和要求，文件读取方式指定列名所在行及对应模型。完整文件核验通过后形成新的登记版本；相关目录、授权和数据流需核对该版本，才能按行处理商品价格。

### 了解数据是否缺失或重复

**业务用途**：先了解数据当前是什么状况，再决定治理要求，避免在不了解缺失、重复和取值分布时盲目制定规则。

**适用场景**：接手客户或商品来源、准备制定质量要求，或需要观察来源异常分布时。

**必选与可选**：按需执行；采样观察适合初步认识数据，最终成果能否发布仍依赖真实完整运行与核验。

**前置条件**：结构化来源可读取，字段加工授权有效；API 业务查询参数须事先声明。

**后续衔接**：数据情况报告为模型约束、质量规则和数据流处理提供依据；发现缺失或重复后，还需确认业务要求，再由来源或处理逻辑修正。检查本身不会清洗数据。

**实际例子**：整理客户表时，先对 id、name、amount 采样1000行，查看编号重复、姓名空值和金额范围。发现空姓名后先确定它是否必填，再配置规则；采样报告帮助发现问题，能否发布仍要依据完整运行和成果核验。

### 数据流与处理节点

**业务用途**：把业务处理要求变成可以重复执行的加工方案，明确每一步从哪里取数、如何处理、怎样检查、最后形成什么成果。

**适用场景**：需要统一客户姓名、筛选订单、关联商品分类、汇总金额或隔离不合格记录时。

**必选与可选**：来源和模型输出必需；清洗、筛选、去重、关联、汇总及质量节点按业务需要配置。引用的版本与约束必须有效，完整运行是产生真实成果的必要条件。

**前置条件**：来源资源及字段加工授权有效；可选择已有模型，或先运行再生成模型。文件要有结构化契约，API 查询参数须事先声明。

**后续衔接**：来源结构由元数据核对，结果要求由模型约定；工作流可以组织多个数据流，调度可直接触发批量数据流或工作流。真实成果经过核验发布后再衔接共享。

**实际例子**：客户来源读取 id、name、amount → 文本转换对 name 去首尾空白；专用业务计算可用 Python / JavaScript 代码节点（金额用 Decimal），并声明完整输出字段 → 质量节点检查 id 非空且唯一、name 非空、amount 不小于0 → 合格分支连接客户模型输出。保存、发布定义并完整运行后，再核验本次成果；去空白不会补全原本缺失的名称。

### 任务编排、成果传递与恢复

**业务用途**：把多个可独立运行的数据处理任务组织成一项完整业务工作，明确先后依赖、失败条件及是否需要人工发布审批。

**适用场景**：客户和商品要并行更新、月报要等待前置成果，或质量核验通过后才允许进入发布审批时。

**必选与可选**：多个任务需要协调时使用；单个数据流可独立运行。任务编码和有效依赖必需，独立质量检查、发布审批按业务需要加入。

**前置条件**：数据流版本已发布并手动验证可用，来源权限持续有效；任务之间不能形成循环依赖。

**后续衔接**：数据流负责具体加工，工作流负责组织任务，调度负责何时启动。发布任务等待有成果维护职责的资产提供方审批；普通申请人不能自审批。

**实际例子**：建立 customers 和 products 两个数据流任务，无依赖时可并行。再加 check_customers 质量检查任务，输入选择 customers；最后加 publish_customers 发布审批任务，成果仍选 customers，并依赖 check_customers 成功。发布由另一位有职责的人员审批。

### 固定间隔与日历调度

**业务用途**：让已经验证可用的业务工作按约定时间重复发生，减少人工记忆和重复启动，同时保留每次触发的依据。

**适用场景**：客户资料需要每日更新、商品价格需要每半小时刷新，或月报需要在指定日历时点启动时。

**必选与可选**：自动执行时按需配置；手动办理不依赖调度。已发布的批量数据流或工作流版本、时间规则及执行权限是调度生效的必要条件。

**前置条件**：先发布并手动验证批量数据流或工作流，确认定时执行的方案可用；调度以执行人的当前权限运行，保存后即启用。

**后续衔接**：工作流规定做什么及任务依赖，调度规定何时开始；实际结果仍由运行运维、质量核验和发布流程确认。数据流或工作流的新版本不会自动替换现有调度。

**实际例子**：客户工作流手动跑通后，需要工作日09:00更新：选择它的已发布版本，日历规则填 0 9 * * 1-5，时区填 Asia/Shanghai，首次触发选择未来时间，预览五次后保存启用。工作流发布 v2 后，已有调度仍使用原选定版本。

### 质量管理：从检查到治理

顶部只保留“质量管理”入口，页内分为“检查记录、检查方案、问题整改、质量趋势”。旧页面地址继续可用。

1. **先选数据并配置要求**：进入数据流，选择来源和字段，在“定规则”中添加“检查数据质量”。直接设置必填、唯一、范围等要求；需要修正数据时，再增加去空白、去重或分类统一等处理步骤。单个数据流可以直接保存并运行，工作流和调度按需使用。
2. **需要复用时保存检查方案**：在当前检查步骤点击“保存为检查方案”，输入字段、参考字段和要求会自动带入。命名后保存草稿，到“检查方案”核对并发布。已发布版本可以点击“在数据流中使用”，选择数据流并进入修订，选中检查步骤后点击“应用到当前检查步骤”。应用会替换该步骤的检查要求，请核对后保存并运行；不自动执行，不改变其他步骤。
3. **查看检查记录**：按真实数据流运行查看，包含未配置检查的执行。列表分别显示运行状态和检查配置，运行完成不能代替质量通过。进入详情后读取当前有权查看的固定版本检查要求、节点计数和实际结果；没有完整报告时查看执行日志，不认定已通过。
4. **发现异常后登记整改**：在存在真实质量失败或隔离记录的运行详情点击“登记质量问题”。原运行和版本直接带入，只需选择责任人及期限。一般执行失败不能作为质量问题登记，服务端仍核对权限、异常、快照和重复登记。
5. **整改后复查并核验成果**：来源问题修正后可在问题中启动原版本复测，满足条件后关闭。若修改了检查或清洗逻辑，应保存为新数据流版本并运行，形成独立证据，不能用新版本成功冒充原版本问题已关闭。有成果的成功运行可进入成果核验，核对质量、完整性及其他发布条件。

“历史成果办理”收起在检查记录底部，仅用于外部已经处理完成的成果登记、来源规则维护和实际结果核验。它不是新数据流的前置步骤。批量检查在实际运行后查看；流式治理在数据流中查看持续运行状态，按需暂停并生成固定成果快照后再核验，不把批量运行记录当作实时质量监测。

### 历史来源质量规则

**业务用途**：把业务对数据正确性的要求写成明确检查条件，供历史治理成果登记和后续质量门禁采用。

**适用场景**：已有治理结果需要补充统一质量依据，或历史客户表需要明确编号必填、唯一及金额范围时。

**必选与可选**：历史成果登记依赖同一来源已发布规则；新开发数据流的检查在数据流检查步骤或检查方案中维护，两类入口各有适用范围。

**前置条件**：先明确检查对象、字段含义、可接受范围，以及哪些失败必须阻止发布。

**后续衔接**：历史成果登记固定来源最近发布的规则版本，绑定真实结果后执行检查。规则发布只确定检查依据，不自动检查、修复或重新绑定已有成果。

**实际例子**：客户历史治理结果需要登记时，可先为同一来源发布“客户编号检查”：id 设置必填和业务主键，均勾选阻断。再登记历史成果、绑定真实结果表并检查；重复编号会阻断。新开发数据流应在检查步骤或检查方案中配置要求。

### 可复用检查方案

**业务用途**：把多条经常一起使用的质量要求组合成一套可复用检查方案，减少不同数据流对同一业务要求的重复配置和遗漏。

**适用场景**：客户日常清洗、客户月报都采用同一套编号与姓名要求，或多个商品流程都要核对分类编码时。

**必选与可选**：复用规则时按需使用模板；也可在数据流质量节点直接配置检查。引用模板时字段契约和版本必须有效。

**前置条件**：检查输入字段及类型明确；跨表参照检查还需要真实参考输入，双方匹配字段类型兼容。

**后续衔接**：模板在数据流质量节点执行并形成运行质量报告；模板更新不会自动改变已有数据流，输出仍需满足模型约定。

**实际例子**：客户日常清洗和月报都要检查 id 非空唯一、name 非空，可保存为“客户基础校验 v1”，让两个数据流的质量节点引用。商品分类需核对分类表时，添加参考输入字段和跨表存在检查，并连接真实参考输入。

### 成果质量与完整性门禁

**业务用途**：判断已产出的成果是否符合业务质量要求，以及处理范围和证据是否足够完整，为发布提供依据。

**适用场景**：准备提供客户或商品成果、核对历史结果，或排查为何成果被阻断时。

**必选与可选**：成果发布需要满足适用质量和完整性门禁；来源、结果有效期、职责等其他发布依据也必须有效。

**前置条件**：已有真实成果；历史登记成果还需来源规则及实际结果绑定，不能仅凭登记信息认定数据存在。

**后续衔接**：自动成果关联固定模型和运行质量证据，历史成果关联固定规则与真实结果核验。异常回到来源或数据流整改，合格成果继续进入发布及共享办理。

**实际例子**：客户成果有1000行，检查显示998行通过、2行阻断。打开明细定位规则及已核对范围，回到来源或处理配置整改；自动成果需要重新完整运行产出新成果后再核验。点击检查不会自动补齐姓名或修改来源数据。

### 质量趋势

**业务用途**：把一段时间的质量表现放在一起比较，判断问题是偶发、持续恶化，还是经过治理后有所改善。

**适用场景**：需要观察客户编号重复是否减少、商品分类异常是否集中在某天，或判断整改是否有效时。

**必选与可选**：按需分析趋势；趋势用于观察和定位问题，不能替代某份成果的质量核验。

**前置条件**：存在包含质量节点的数据流实际运行；没有对应检查事件就没有趋势数据。

**后续衔接**：异常日期关联到运行运维中的真实节点诊断，再进入质量整改；改进效果由后续运行证据体现。

**实际例子**：客户某日检查1000行、隔离20行，隔离比例为2%。查看最近30天趋势，按该数据流到运行运维查当日诊断，再登记整改。若同一份数据经过两个质量节点，检查行次可能为2000，不能理解为2000名客户。

### 质量整改闭环

**业务用途**：把已发生的数据质量问题交给明确人员处理，并用真实复测证据证明问题已解决，形成可追踪的整改闭环。

**适用场景**：客户姓名缺失、编号重复或商品价格异常已在真实数据流运行中出现，需要分派责任与跟踪期限时。

**必选与可选**：有需跟踪的异常时使用；关闭问题必须有同一数据流版本的成功复测且无隔离记录。

**前置条件**：真实运行包含质量失败或隔离证据，整改责任人与未来处理期限明确。

**后续衔接**：运行诊断说明问题发生在哪里，整改记录说明业务原因和修正过程；复测验证原问题是否消除。未关闭问题还会阻止相关成果清理。

**实际例子**：客户清洗因姓名缺失产生隔离。新建问题并选择该真实运行，分派本部门维护人员、设期限；记录来源补正情况后启动原版本复测。复测成功且无隔离时核验关闭。修改流程版本不能代替原问题的同版本复测。

### 血缘与影响分析

**业务用途**：说明一份数据从哪里来、经过哪些处理，以及某项变更会影响谁，帮助解释结果和安排变更。

**适用场景**：需要追溯客户姓名或商品价格来源，或准备调整模型、替换成果、停用来源时。

**必选与可选**：追溯和评估变更时按需使用；分析只解释已登记关系，不会自动修改对象或迁移下游。

**前置条件**：当前人员有对象可见权限；字段血缘需要实际完成的数据流运行证据。

**后续衔接**：模型、来源和数据流的变更应结合影响分析安排修订；成果替换与清理还依赖迁移和生命周期规则。受限依赖需由对应责任人核对。

**实际例子**：调整客户模型的编号类型前，复制模型定义编号，选择“治理定义”并分析影响，确认依赖的数据流与成果。追溯具体成果的姓名来自哪里，则打开已完成运行的字段与转换。安排下游迁移后再发布变更，分析本身不会替换引用。

### 运行运维

**业务用途**：把不同治理工作的真实执行记录放在一起，区分方案是否可用、哪次执行出了问题，以及需要修复什么条件。

**适用场景**：客户流程失败、调度未按预期完成，或需要核对剖析、数据流和工作流的实际处理结果时。

**必选与可选**：存在运行需要追踪时使用；是否成功必须依据实际状态和证据，不能只看定义是否发布。

**前置条件**：已经产生对应运行，当前人员具备可见和处理权限。

**后续衔接**：来源或权限问题回到共享交换处理，方案问题回到数据流或工作流修订，质量问题进入整改；成功成果继续核验发布。

**实际例子**：客户清洗失败时，点击运行编号查看失败节点。若来源授权失效，先恢复所需字段的加工权限，再重跑固定版本；若质量不合格，先处理来源问题。新、旧运行分别保留，旧失败记录不会被覆盖成成功。

### 站内告警与通知

**业务用途**：让需要处理的运行失败和质量异常主动变成通知，帮助业务人员及时知道哪项治理工作需要关注。

**适用场景**：日常客户清洗由调度自动执行，不能依靠人员一直查看运行列表时。

**必选与可选**：需要主动提醒时按需配置；规则默认关闭，启用后才监测后续运行，告警不会自动修复问题。

**前置条件**：当前账号有相关运行；外部通知目标须获管理员批准，地址留空时仅生成站内告警。

**后续衔接**：告警指向真实运行及诊断，再由运行运维、来源维护或质量整改处理。规则覆盖本账号后续运行，不按规则名称自动限定某个业务流程。

**实际例子**：新建“日常治理监测”，启用失败与中断检查，隔离比例门槛填0.05，接收地址留空。启用后，本账号后续完成的运行失败或隔离比例超过5%会生成站内告警。规则覆盖本账号运行，当前不按名称只限定客户流程。

### 保留、清理与迁移

**业务用途**：控制历史成果快照的存储占用，同时保护仍在发布、共享、整改或被下游使用的数据，避免清理破坏在用业务。

**适用场景**：日常治理不断产生历史成果、需要清理过期数据，或要以新成果替换旧成果时。

**必选与可选**：清理与迁移按需办理；最低保留时间、发布状态、授权、整改及依赖保护不能因清理需求而跳过。

**前置条件**：成果属于当前人员可维护的自动治理范围，至少保留24小时；实际使用关系需要先核对。

**后续衔接**：保留策略决定候选范围，依赖预检决定是否能清理；在用成果先安排下游迁移或下架，清理后仍保留定义、运行、质量和血缘证据。

**实际例子**：客户清洗每天产生新成果。先对旧成果做清理预检；若仍在发布或被月报引用，先处理下架与迁移。只有超过最低保留时间且无阻断项时，才输入完整编号确认清理。清理后行数据不可恢复，运行与质量证据仍保留。

### 保留策略

**业务用途**：为重复产生的历史成果约定保留多久、至少留几份，在控制存储的同时保留必要的近期业务依据。

**适用场景**：每天更新客户或商品成果，希望长期运行后仍有可控的历史保留范围时。

**必选与可选**：按需启用自动清理；策略默认关闭。保留期限和最近份数共同保护成果，仍需通过在用依赖检查。

**前置条件**：对应数据流已经存在，管理范围是本人产生的成果；启用前需核对完整数据流编号。

**后续衔接**：策略使超期且超出最近保留份数的成果成为候选，生命周期检查继续保护已发布、被引用或涉及整改的成果，不强制清理在用快照。

**实际例子**：客户清洗设置保留30天、最近保留3份，先以关闭状态保存并核对数据流。启用时输入完整数据流编号。超过30天但仍在最近3份中的成果会保留；已发布或被引用的成果也不会因到期强制清理。

### 下游成果迁移

**业务用途**：把依赖旧成果的业务逐步转到兼容的新成果，明确哪些引用已切换、哪些还需处理，避免直接清理旧数据导致下游中断。

**适用场景**：客户成果升级、商品模型变化或旧来源准备退役，而月报等下游仍引用旧成果时。

**必选与可选**：替换在用成果时按需办理；目标兼容、实际可用及旧依赖消除是完成迁移的必要条件。

**前置条件**：旧、新成果在同部门且可用；字段类型、主键、空值、精度与敏感范围兼容。

**后续衔接**：迁移计划可协助生成下游数据流草稿，实际发布与完整运行仍由数据流办理。目录挂接及共享、加工授权分别处理，审批和授权不会自动复制；完成后才考虑旧快照清理。

**实际例子**：客户基础信息有新成果，要让月报改用新版：登记旧、新成果迁移，选择引用旧成果的月报数据流并生成草稿。核对、发布和完整运行新版，再处理旧引用、挂接与授权；旧依赖全部消除后核验完成迁移。

### 物理模型目标建表

**业务用途**：把物理模型中约定的结构落实为数据库中的新空表，让后续数据写入有确定的存放位置。

**适用场景**：客户或商品结果需要落到新的 PostgreSQL 或 MySQL 库表，而目标表尚不存在时。

**必选与可选**：只有需要新建目标表时使用；普通逻辑模型或平台成果不必建表。模型版本、真实目标权限和预检通过是执行前提。

**前置条件**：物理模型已发布，目标库或 Schema 已存在，当前人员有数据源运维权限，目标凭据允许建表。

**后续衔接**：模型提供结构约定，预检核对真实目标，执行记录保留结果。建表只创建空表，不创建 Schema、外键或覆盖已有表；数据写入由共享交换的数据同步另行负责。

**实际例子**：物理商品模型的目标为 governance.dim_product。选择真实 PostgreSQL 或 MySQL 数据源，预检建表语句，再输入完整表名确认。目标已存在会阻止创建；成功也只创建空表，写入商品数据需另配共享交换的数据同步。

### 登记历史治理数据集

**业务用途**：将平台之外已经整理好的历史数据纳入统一治理依据，补齐来源、规则、实际结果和完整范围的联系。

**适用场景**：企业已有历史客户清洗表，需要纳入平台质量核验和共享管理，而不是重新开发一套加工流程时。

**必选与可选**：已有历史成果按需登记；新开发的数据流自动生成成果。真实结果绑定和质量、完整范围核验是历史成果发布前提。

**前置条件**：来源已有发布的质量规则且含 id 字段；办理人员具有资产提供方职责、来源维护和加工授权。

**后续衔接**：登记固定最近发布的来源规则版本，实际结果绑定证明数据放在哪里、如何对应字段，完整核验后才进入质量检查与成果发布。登记本身不复制或生成数据。

**实际例子**：已有一张历史客户清洗结果表：先为来源发布质量规则，在发布管理登记历史治理数据集，再绑定实际结果表，核对字段和完整范围并检查。只登记名称与字段不会复制那张表，也不能直接发布未核验结果。

### 治理成果核验与发布

**业务用途**：判断这一次成果当前是否有足够依据提供给后续业务，并将可提供的成果纳入资产发布管理。

**适用场景**：客户或商品数据已经整理完成，准备交给下游业务或进入共享编目时。

**必选与可选**：实际质量、完整性、来源依据、结果有效期及发布职责均须满足；是否继续跨部门共享根据用途办理。

**前置条件**：已有真实成果，当前人员具有本成果维护与资产发布职责；历史成果还需有效实际结果绑定。只有工作流任务处于待发布审批时，才有工作流审批事项；普通成果直接按成果核验与发布流程办理。

**后续衔接**：数据流提供运行与模型证据，质量检查给出适用结论，发布时重新核验当前依据。发布后还需按用途办理目录挂接、审核、使用申请及授权，不自动公开到门户。

**实际例子**：客户清洗完整运行得到1000行成果。打开本次成果，核对固定模型、来源版本、质量和完整性，再重新核验条件；当前依据有效时由有职责人员核验发布。超过有效期先重新运行数据流生成新结果；其他部门使用还需挂接、审核与使用授权。

### 工作流成果发布审批

**业务用途**：由有职责的人员核对工作流提交的成果及发布依据，在自动处理与正式提供之间保留必要的责任确认。

**适用场景**：业务工作流已经完成加工和检查，仍需另一位有权人员确认成果可发布时。

**必选与可选**：仅有发布审批任务的工作流需要此环节；普通申请人不能自审批，批准仍须通过服务端当前门禁。

**前置条件**：工作流已到待发布审批阶段，审批人具有对应成果维护和资产提供方职责。

**后续衔接**：上游任务提交真实成果和质量计数，批准后发布成果并推进工作流，驳回保留理由。后续目录挂接与使用授权仍按共享交换职责分别办理。

**实际例子**：客户工作流停在发布审批时，有成果维护职责的资产提供方打开待审批成果，核对申请人、成果编号和质量证据，填写依据并批准；条件不满足则写明原因驳回。通过后工作流继续，其他部门仍需申请使用授权。

## 常见问题

### 运行成功，为什么成果不能发布？

先区分样本试运行和完整运行，再检查是否已绑定发布模型、质量与完整性是否通过、结果是否仍有效，以及来源和职责是否有效。

### 为什么数据建模里找不到刚生成的模型？

确认选择了“根据结果生成模型”，并完成真实完整运行；检查当前治理空间和模型草稿列表。优先从该次运行的“查看已生成模型”入口进入，历史运行可补建草稿。

### 保存后为什么数据没有变化？

保存只保留方案。要让修改作用于数据，必须通过检查并实际运行；工作流和调度还需确认引用的是正确的已发布版本。

### 其他部门整理的数据，成果归谁？

单一来源的治理成果保留原提供部门归属，治理空间仍记录实际执行过程；共享目录默认关联原目录。处理人员、执行空间和数据提供部门可以不同。

### 从哪里办理来源接入和共享授权？

阅读[共享交换操作指南](/guides/exchange)。操作指南只提供说明，实际业务状态、权限、审批和校验始终以对应业务页面为准。

## 治理成果的 API 交付

需要外部系统按参数查询治理结果时，先完成成果核验及发布，再进入共享交换的“数据服务”定义查询接口。目录审核、使用申请、外部调用凭据、字段授权和调用审计均由共享交换管理。数据流继续负责关联、清洗与质量检查，不把接口发布作为必经步骤。具体操作参见共享交换操作指南“把治理成果提供为查询接口”。

## 受理资产使用反馈

入口：[质量管理 → 使用反馈](/platform/governance/quality?tab=feedback)。资产使用者可反馈质量、更新、字段口径和访问交付问题。受理列表按处理部门隔离；选择空间时展示当前空间及无需空间处理的来源反馈。

查看用户描述后填写公开回复。确认属于治理结果问题且拥有原运行访问权限时，可关联整改单；同一运行已有未关闭整改单会复用。新建需要指定责任人及期限，不会自动启动数据处理。已关联整改的反馈必须在真实复测通过、整改单关闭后才能标记完成。

没有关联治理运行的来源数据或接口问题，可联系提供部门核实后公开回复。接口会更新来源时，不能直接把使用者反馈绑定到当前最新结果，以免把问题版本认错。内部整改笔记和执行日志不会自动进入公开回复，请勿手动粘贴敏感信息。


### 轻量处理的格式检查

“检查数据质量”可直接选择大陆手机号、邮箱、日期（YYYY-MM-DD）、整数、小数和不含空白字符。格式检查保留文本原值，不转换号码或金额；缺失值另加“必填”。日期规则检查年月日的书写格式与基本月份/日期范围，不验证闰年或真实日历日期。开启“失败进入隔离分支”后，可在运行结果查看不合格记录及对应要求。

“自定义处理”的示例和输入字段可按需展开，输出字段声明在配置区展开修改；代码编辑区内部滚动。语言切换仍保留各自草稿，固定环境和输出契约继续在运行时核验。

## 持续数据监测与异常复核

入口：“监控与追溯 → 持续数据监测”。选择已授权来源和字段，配置空值率、重复率、行数波动与分布变化阈值，以及监测间隔。首次完整监测固定比较基线；后续不会自动覆盖基线。调整配置会建立新配置版本并重新建立基线，排队与运行中不能修改。

业务时效必须指定实际业务时间字段；支持带时区时间或 `YYYY-MM-DD`。系统逐值解析后取实际最大时间，不将读取成功时间作为业务更新时间。缺少、无效或敏感时间显示“无法核实”。分布比较只使用完整、未截断且非敏感的频次，不能核实的字段不会推断为正常。

发现异常后，点“问题整改”进入统一工单，指定本部门责任人和期限。在来源或数据流完成整改并保存处理记录后，从工单“启动复测”，平台按原配置与固定基线执行完整监测，核验通过后关闭并同步观察状态。配置或基线变化时不能用新规则关闭旧问题。派单、进展与逾期提醒在治理告警的“整改通知”查看。暂停监测不会删除历史。账号、来源或加工授权失效时停止读取；历史详情也重新核对来源权限。

## 标准落标与实际核验

入口：“标准与规范 → 标准落标”。覆盖率表示已发布模型或元数据说明中的字段关联了有效标准版本，不代表数据合格。点“维护关联”回到原模型或元数据维护新版本；确认发布后再核验。

点“核验数据”，选择有权来源，固定标准版本并完整读取，检查类型、空值、长度、精度、格式及允许值。结果提供实际行数、违规数量与最多二十个示例行号，不返回原始字段值。敏感字段无法明文核实，单独标明，不把脱敏占位符当作符合标准。超过读取上限会失败，不会将部分读取标为完整核验。发现违规时点“登记整改”，进入统一派单与期限管理；复测固定原来源、字段、参数及标准版本，完整核验无违规后方可关闭。

## 变更发布与历史恢复

入口：“检查与交付 → 变更发布”。先保存最新草稿，再提交候选，填写变更原因；系统固定最近已发布版本作为比较基准，记录差异及当前有权查看的影响引用。破坏性变更需说明下游迁移和恢复安排。

数据流与工作流必须完成本候选的完整试运行，且没有隔离记录；工作流按固定子版本真实执行，前置结果仅在试跑内部传递，审批节点只核验而不执行正式发布。试运行保留实际结果证据，不登记共享成果或建议模型。其他定义核对结构与引用后独立审核。申请人和候选版本建立人不能审核自己的申请。审核通过后再正式发布；进入变更流程的候选不能从旧发布入口绕过审核，旧候选的批准不能用于新版本。

空间设置可选择数据模型、数据流、工作流、主数据、场景方案与检查方案的必审范围。只有本部门空间责任人或管理员可调整，必须填写原因；启用后，即使没有变更申请，旧发布入口也不能绕过独立审核。共享标准、术语及元数据沿原有全局权限管理。

“恢复历史”引用旧的已发布定义建立新草稿，保留旧版本，继续按变更流程审核。该操作不会回滚来源数据、删除新结果或覆盖历史快照。

## 主数据实体与人工确认

入口：“准备数据 → 主数据管理”。先在数据建模发布实体模型，再选择固定模型、非敏感精确匹配键、最多四个授权来源、各来源非空唯一内部编号及逐字段映射。多字段键共同相等才匹配；没有键的记录计入未匹配数量，不自动模糊合并。

发布定义后点“匹配实体”，实际完整读取各来源生成实体候选与冲突字段。各来源依次读取，跨来源不具备统一事务快照。逐字段选择保留哪个来源的值，填写确认原因后生成实体版本；敏感值保持脱敏。来源内部编号与确认选择保留在候选和版本记录中。

确认版本不可覆盖，后续确认生成递增新版本，并检查版本冲突。查看候选和历史时仍需当前来源及派生权限。点“形成成果草稿”固定当前定义下本人匹配的已确认实体版本，建立普通数据流。后续确认不会改写已固定快照；执行仍重新核对原来源、派生权限及模型版本。通过正常发布、运行与成果核验后可登记目录，并在同一目录挂接数据库和接口呈现。内部快照仅本人使用，不作为共享原始资源，不自动公开或回写业务主档。登记和交付成果仍须追溯原来源“允许派生、允许共享”的有效批准依据。

## 指标口径与实际计算

入口：“标准与规范 → 指标口径”。选择授权来源，配置分组维度、过滤条件、统计项和固定统计区间。支持非空值计数、求和、最小值与最大值；没有分组维度时对完整范围汇总。固定区间包含开始时刻、不包含结束时刻。

保存后生成相同口径的数据流草稿，提交变更完成完整试运行与独立审核，再按已发布版本计算。来源、字段、处理步骤和结果血缘沿用数据流机制。需要修改口径时建立新版本，不直接改写已发布结果。

可选择已发布结果模型；未选择时，实际运行后建立建议模型草稿，到成果核验确认模型与完整性，再按现有流程登记共享成果。定义发布、运行成功与成果发布分别办理。

## 场景方案与重新绑定输入

入口：“处理数据 → 场景方案库”。选择已发布批量数据流或工作流版本，填写业务范围及验收要求；系统保存固定引用和每个输入槽位的字段契约。招生报名、人口信息、法人信息、死亡人口专项、矛盾调解和不动产应用可分别维护方案。

方案发布后点“建立实例”，为每个输入槽位重新选择当前有权来源及所需查询参数；字段类型、精度和敏感范围必须兼容。实例不继承原来源的凭据、固定查询参数或加工授权，也不会伪造验收通过或业务运行结果。

数据流方案生成独立草稿。工作流方案先生成独立子数据流草稿，在“工作流实例办理”查看子任务，分别复核发布后点“生成工作流”，得到引用这些新版本的工作流草稿，再按现有流程发布和运行。

## 六类业务治理初始化

先完成21张业务来源及六份资产初始化，再执行治理场景初始化。招生报名、人口、法人、死亡人口、矛盾调解、不动产分别建立编号标准关联、完整落标核验、每日质量监测、分类统计与可复用场景方案；人口和法人另有实体匹配候选。主数据确认与独立发布审核由实际治理人员办理，初始化不替人员确认。统计口径修订完成完整试跑后保持待审核。两个初始化登记独立保存检查点，迁移后可续执行，不重建原表或覆盖原资产。

### 配置变化后的问题整改

“启动复测”保留原运行参数、字段、来源契约及工作流输入绑定；关闭时再次核验同一检查依据。变更发布试跑须回到原变更单办理，不能从整改入口转为正式执行。

原规则、基线或来源契约已经变化时，先对同一业务运行新的完整检查；仍有异常的，先登记新的整改工单。在旧问题填写处理进展和新运行编号，选择“关联验证并替代”。旧问题显示“已替代”，保留原异常、原运行和新验证链接，不会被算为原检查通过。资产反馈若仍关联未完成的后续工单，继续等待整改。

### 批量确认主体

在主数据运行的候选列表按“尚未确认”筛选，勾选本页候选（每批最多100个），选择“预览批量确认”。核对中文字段、脱敏结果和来源编号，填写确认原因后选择“确认所选实体”，才会生成不可覆盖的实体版本和审计记录。

有冲突的候选、已有实体的修订，以及跨来源敏感值无法判同的情况，仍使用逐字段确认。预览后若候选、权限或实体版本变化，整批拒绝；刷新并重新预览，不会只保存半批。敏感占位值相同不代表原始值相同。

### 中文名称和通知

模型修订中分别维护“中文名称”和“业务含义”。历史模型的空白名称按同模型已提交成果或显式来源映射补充展示；使用“带入已核实中文名称”只修改当前草稿，保存新版本后办理审核，历史版本不变。

治理告警的“整改通知”支持全部、未读及已读筛选。“标记已读”保留首次阅读时间；顶部“刷新”同时更新通知、告警记录和规则。只显示当前账号仍有权处理的问题通知。

## 数据沙箱与轻量治理

进入“处理数据 → 轻量治理”，切换到“SQL 数据沙箱”创建私人沙箱，输入逻辑表名并上传 CSV。导入字段默认按文本保留，前导零不会丢失；计算数值请显式使用 CAST。选择表名可查看字段并填入 SELECT 示例。支持单条 SELECT、WITH、JOIN、GROUP BY；运行预览后可从历史重开 SQL，也可输入新表名保存完整结果。

每份 CSV 最多 20 MiB、100 列、100000 行；每个沙箱最多 8 张表、80 MiB，每个账号最多 4 个活动沙箱。普通沙箱 7 天到期，完整公开体验按当前登录隔离并在 24 小时后到期。关闭或到期后无法继续使用。排队和运行中的查询可取消，失败与未知状态显示在历史中。

就绪表可下载 CSV 或“送入轻量治理”。CSV 的 NULL 下载为空字段；移交轻量治理保留 NULL 与空串差异。移交后自动选择文件，仍需自行命名单元、保存和运行。已移交文件独立于沙箱存活。

数据沙箱采用 MySQL 兼容的 SELECT 语法：整数使用 `CAST(字段 AS SIGNED)`，小数使用 `CAST(字段 AS DECIMAL(30,6))`；不要将数据库建表类型 `BIGINT` 直接当作 MySQL CAST 目标。保存为新逻辑表由后端执行受控库化，不直接开放用户DDL。
